# 2026-08-06 — Session Log

## Summary

Implemented and hardware-verified **A.2 (minimum control plane)** end to
end: the pc-app can now select which 2 of 128 RHD2164 channels stream,
gated by explicit `STOP_STREAMING`/`SET_CHANNELS`/`START_STREAMING`
sequencing with real MCU-confirmed acknowledgments — not timers, not
guesses. Getting there required three failed MCU-side placements for
`SET_CHANNELS`'s SPI0 work before landing on the right architecture (Manuel's
call: gate FPGA sample ingestion at the source via a new regbank register,
rather than racing a continuous 30 kSPS producer from the MCU side), then a
full afternoon of live bench testing that surfaced — and fixed — two more
real bugs: a reentrancy bug in the MCU's command handling, and a silent
USART overrun on the WB09KE bridge that could permanently kill command
relay for the rest of a session. Every fix in this log was verified against
real hardware before being considered done, per the standing rule for this
work: *"we should not call them done unless we verify they work
successfully."*

By the end of the session: single-click and rapid-repeat-click reliability
both confirmed live, the earlier rapid-click MCU crash-loop no longer
reproduces, and all temporary diagnostic instrumentation has been reverted
to a clean, production-ready baseline (the underlying fixes stay; the noisy
debug scaffolding used to find them doesn't).

## 1. The MCU hang saga — three failed placements before the redesign

`SET_CHANNELS`'s SPI0 write+readback work (6 blocking transfers plus a GATT
notify) has no location inside the live 30 kSPS streaming hot path that's
provably safe to run from:

1. **Inline in the BLE event-handler callback** (`STREAM_APP_OnCommandWrite`)
   — hung the MCU under repeated calls.
2. **A standalone `UTIL_SEQ` task**, deferred via `UTIL_SEQ_SetTask` — never
   ran. Root cause never fully identified despite checking masks, priority,
   and registration; abandoned.
3. **Checked-at-loop-entry, debounced** — survived a single call, but hung
   after 6-7 rapid clicks. Traced to stacking extra SPI0/notify work onto an
   already-busy packet iteration.

Manuel's question — *"isn't it easier to send the STOP/START command down to
the FPGA?"* — reframed the whole problem: instead of finding a safe moment to
interleave `SET_CHANNELS` with live streaming, remove the need to interleave
at all. `SET_CHANNELS` now requires the stream to already be stopped, with
explicit `STOP_STREAMING`/`START_STREAMING` opcodes (`0x02`/`0x03`) added to
the 0xFFF1 command protocol.

## 2. FPGA-side ingestion gate (Manuel, RTL)

Initial redesign attempt flushed the FPGA FIFO by having the MCU pop-and-
discard until empty — but this raced the FPGA's continuous 30 kSPS producer
and, in bench testing, never actually won: the flush always hit its safety
cap (tried 4096, then 16384 pairs) regardless of how high the cap was
raised.

Manuel's fix: gate ingestion **at the source**. New regbank register, addr
`36` (word `164`, chosen because addr 6-35 are reserved for a future
reduced-rate multi-channel mode): bit 0 = `stream_enable`, ANDed directly
into `fifo_wen` inside the `ch_sel` module (`components.v`). `STOP_STREAMING`
now disables ingestion *first*, confirmed via SPI0 readback, and only then
flushes — draining a static backlog instead of racing a moving one. Caught
one bug before it was flashed: the register's reset default initially
defaulted to `0` (disabled) rather than `1` (streaming) — Manuel confirmed
and fixed to `1`.

## 3. Command reentrancy — found in a bench log, not hypothetical

While investigating why the flush still occasionally hit its safety cap even
with the FPGA gate in place: `StreamFlushFpgaFifo()`'s periodic
`BLE_STACK_Tick()` calls (needed to avoid one long blocking stretch) let a
brand-new incoming command get processed *while the previous one was still
mid-flush* — nothing protected the shared pending-state
(`s_streaming_stopped`, `s_pending_ch_a/b`, `s_set_channels_pending`) against
this. Debug log showed a new `STOP_STREAMING`+`SET_CHANNELS` cycle's prints
interleaved inside a still-running previous flush's own prints; the
matching pc-app symptom was a `SET_CHANNELS` that arrived mid-flush and got
silently orphaned. Fixed with `s_command_busy`, held for the duration of
each pending-branch's work, rejecting any command that arrives while busy —
makes one full STOP/SET/START cycle atomic.

## 4. Real MCU-confirmed acks (section 5.6) — replacing timer guesses

Before this, `STOP_STREAMING`/`START_STREAMING` were fire-and-forget: the
pc-app fired the command and waited a fixed settle delay, then assumed
success. Manuel asked directly whether the MCU's completion was actually
being verified — it wasn't, so this was implemented the same session.

- **MCU**: `FPGA_SPI_SetStreamEnable()` is now always followed by
  `FPGA_SPI_ReadStreamEnable()` — a real SPI0 readback, not just "the write
  call returned." `STREAM_NotifyStreamingAck(cmd, success, conn_handle)`
  sends the result over 0xFFF3, whether or not the readback matched.
- **Protocol**: 0xFFF3 (previously `SET_CHANNELS`-readback-only) is now
  type-prefixed so all three command responses share one characteristic:
  `0x01` = `SET_CHANNELS` readback (`[type, ch_a, ch_b]`), `0x02`/`0x03` =
  `STOP`/`START_STREAMING` ack (`[type, success]`). Type values deliberately
  match the 0xFFF1 command opcodes, so a response self-identifies what it's
  answering.
- **pc-app**: `main_window.py`'s Apply sequence now waits on real
  `stop_streaming_ack`/`start_streaming_ack` signals (`STREAMING_ACK_TIMEOUT_MS
  = 2000` fallback per step, same reasoning as the existing SET_CHANNELS
  verify timeout) instead of fixed `QTimer.singleShot` delays.
  `APPLY_COOLDOWN_MS = 1000` — a fixed pause after a full cycle completes,
  before the Apply button re-enables — was added separately, see §6.

Full protocol detail in `docs/interfaces/channel-selection-control-plane.md`
section 5.6.

## 5. Bridge command-relay silently dying mid-session — found, root-caused, fixed

First live hardware test of the ack mechanism surfaced a new failure: after
2-6 successful Apply cycles, every subsequent command would simply vanish —
pc-app sends it, but *nothing* on the MCU's UART or (once instrumented) the
bridge's own relay log ever shows it arriving. Live streaming would stay
stopped and the pc-app's Apply button would show "no response" forever.

**Diagnosis required building visibility that didn't exist.** The bridge's
debug trace (`CFG_DEBUG_APP_TRACE`) was off by default, and its
connection-sequence log macro (`DT_INFO_MSG`) was *unconditionally* silenced
even when trace was on — both because the bridge's only UART (`USART1`, 2
Mbaud) is the exact same wire the pc-app uses for live data and commands.
Enabled trace, routed `DT_INFO_MSG` through it, and added log lines that
didn't exist before: connect/disconnect events (previously totally silent)
and command-relay success (previously only failures were logged). Since two
processes can't safely share that port (confirmed earlier this session — a
second reader corrupts the pc-app's own stream), the pc-app itself was
temporarily modified to print whatever non-magic bytes it discarded during
resync, surfacing the bridge's debug text without a second port reader.

**Root cause, confirmed live**: `stm32wb0x_it.c`'s `USART1_IRQHandler` never
checked or cleared the USART **overrun-error (ORE)** flag. Per the STM32
USART reference manual, once ORE latches, RXNE stops being set for new data
until it's explicitly cleared via `ICR.ORECF` — one overrun (plausible at 2
Mbaud if the BLE radio's own higher-priority ISR delays servicing a byte
past its ~5 µs window) silently and *permanently* killed command reception
for the rest of the session, with zero log output anywhere in the existing
code. Fixed: check + clear `LL_USART_IsActiveFlag_ORE`/`ClearFlag_ORE` every
ISR entry, with a log line.

**Confirmed live the same session**: after reflashing, 6 consecutive Apply
cycles succeeded, then the bridge logged `USART1: RX overrun (ORE) cleared`
mid-`SET_CHANNELS`, and recovery was immediate — `START_STREAMING` sent
right after relayed and applied normally. The fix converts a fatal,
permanent failure into a survivable, self-healing, single-command loss.

**Residual gap, mitigated not eliminated**: a single command can still
occasionally be lost to an overrun with no retry. Two overruns in one
session both landed on `SET_CHANNELS` specifically — suspected reason: the
ack-driven design sends the next command the instant an ack arrives, with
zero deliberate gap, which tends to land `SET_CHANNELS` right as the bridge
is still busy relaying the `STOP_STREAMING` ack's own GATT notification
event. Added `COMMAND_GAP_MS = 15` (pc-app) — a small deliberate delay
between receiving an ack and sending the next command — to reduce (not
eliminate) how often this collision happens. Also updated the pc-app's
timeout-path messaging from a now-stale "no response (RTL readback not
available yet?)" — written when timeouts mostly meant a missing RTL
feature — to an explicit "✗ ... unsuccessful — no confirmation received",
since a timeout today usually means a real dropped command.

**Confirmed live**: many clicks in a row after the mitigation, only one hit
the overrun (down from 2-in-~8 before), degraded exactly as designed
(honest failure message, streaming stayed live, zero stuck state), and the
very next click cleanly verified.

## 6. Rapid-click crash-loop — re-tested and confirmed fixed

Earlier bench testing (before this session's ack work) found that rapid
Apply-clicking (~10+ clicks at human speed) could put the MCU into a
repeating crash/reset loop (`tio` showed the USB device cycling
disconnect/reconnect every ~1.0-1.7s). Root cause was scoped as a known
limitation by Manuel's explicit decision — real usage is occasional channel
selection, not rapid button-mashing — but the *software* gap that made it
reachable at human clicking speed was fixed: `START_STREAMING` was
fire-and-forget, so the Apply button re-enabled the instant the bytes were
sent, letting a human sustain close to 1 cycle/second by clicking normally.
`APPLY_COOLDOWN_MS = 1000` (enforced after a cycle completes, before the
button re-enables) made that rate physically impossible to sustain.

**Re-tested and confirmed this session**, after the full ack-driven redesign
plus `COMMAND_GAP_MS` and the ORE fix all landed: sustained rapid-click
bursts no longer reproduce the crash-loop. The button stays inactive through
the full cycle (the Verified mark lands *before* the button re-enables,
confirming the ack-driven sequencing is genuinely gating the button, not
racing it), no reset loop, live streaming continued throughout. Root
electrical cause remains un-investigated by deliberate scope decision — not
blocking, since the trigger condition is no longer reachable through the UI.

## 7. Cleanup — reverting temporary diagnostic instrumentation

Once the ORE root cause was confirmed, all temporary diagnostic-only
additions were reverted to keep the shipped state clean:

- pc-app: removed the per-command `print()` calls in `send_command()` and
  the `_print_bridge_debug()` resync-garbage printer in `serial_reader.py`.
- Bridge: `CFG_DEBUG_APP_TRACE` back to `0` (off by default — same UART as
  the data stream). `DT_INFO_MSG` stays wired through `APP_DBG_MSG` (rather
  than a separate hardcoded no-op) so flipping that one flag re-enables all
  of today's new logging for a future debug session without re-deriving it.
- The real fixes — ORE clear, `s_command_busy` reentrancy guard, ack-driven
  sequencing, `COMMAND_GAP_MS`, clearer failure messaging — all stay.

Bridge rebuilt with a full `make clean` (the Makefile doesn't track header
dependencies, so a header-only revert like this needs a forced clean build
to actually take effect) and reflashed.
