mid-way through hardware-instrumented diagnosis of the ~10 ms gap after a BLE

### 1.2 Conclusion — both H1 and H2 rejected

The CPU is not stuck in a single `UTIL_LPM_EnterLowPower()` call, and there's no
MCU-side scheduling anomaly. It's sleeping and waking on its completely ordinary
~2 ms cadence the entire time — indistinguishable from any other idle period. The
"extra ~10 ms" is not an app-side bug at all: it's simply several ordinary ~2 ms
sleep cycles elapsing while `s_txFlowOff` stays set, waiting for
`ACI_GATT_TX_POOL_AVAILABLE_VSEVT_CODE` to actually fire — which lives entirely
inside the closed-source BLE stack's internal TX-pool-refill timing. **This is not
something further app-side instrumentation of the resume path can fix.**

This closed the "why is there a gap" question and reframed the goal: the BLE
stack's stall behavior can't be fixed or debugged further from the app side — the
only lever left is preventing the stall from *costing data*.

## 2. "Given closed-stack stalls are unavoidable, can we hit zero data loss?"

User's question, verbatim: *"If so, then we need to be able to work around those.
My question is, given this, can we achieve our goal of no data loss/no SKPs?"*

### 2.1 FPGA FIFO capacity check

Checked the actual instantiation in `kuntur_fpga.v:178-181`:

```verilog
fifo #(
    .DATA_WIDTH (32),
    .ADDR_WIDTH (10)
) fifo0 ( ... )
```

`ADDR_WIDTH=10` → 1024 entries deep. At 30,000 pairs/s that's **~34 ms of
hardware buffering headroom** — comfortably more than the ~22 ms outlier stall
just measured in §1, and far more than the typical few-ms stalls from the earlier
UART log.

### 2.2 The actual bug: SPI polling was gated by the same flag as BLE sending

`stream_app.c` (pre-fix):

```c
if (s_txFlowOff)
  return;

while (1)
{
  ...
  FPGA_SPI_ReadSamples(pkt.samples, STREAM_PAIRS_PER_PACKET);   // ← SPI poll
  tBleStatus ret = STREAM_NotifyData(&pkt, ...);                 // ← BLE send
  ...
}
```

`FPGA_SPI_ReadSamples()` only ever ran from inside the same loop that sends BLE
notifications, gated by the same `s_txFlowOff`. The instant BLE stalled, SPI
polling stopped dead too — even though the FPGA FIFO had ~34 ms of room to spare.

Also found: the file's own header comment already described the *right*
architecture —
`SPI DMA ISR → STREAM_APP_IngestSamples() → ring buffer → StreamSendTask()` — but
`grep`ing the whole App/ tree for `STREAM_APP_IngestSamples` and `ring buffer`
turned up **nothing** — it was a stale, aspirational comment from before the
"Phase 1 tight loop" experiment collapsed ingest+send into one synchronous path
for throughput, and it was never split back out.

### 2.3 User pushback — throughput risk

User, verbatim: *"Hold on. I am confused. If I remember correctly, We went to
have the FIFO in the FPGA to streamline the BLE throughput. I think if we add a
ring buffer in the MCU we might reduce the throughput?"*

Valid concern, grounded in the file's own history. `stream_app.c:15-18`
documents that an earlier `UTIL_SEQ`-scheduled architecture couldn't hit
30k SPS, which is why the code was rewritten as one tight synchronous loop
bypassing the scheduler entirely:

> *BLE strategy: tight notify→BLE_STACK_Tick loop (Phase 1 experiment). Direct
> BLE_STACK_Tick() call bypasses UTIL_SEQ __WFE() sleep. If batch ≥ 4 at
> flow-off, UTIL_SEQ was the bottleneck → 30k SPS possible.*

Resolution: don't add a separately-scheduled ingestion task (which would
reintroduce that exact overhead). Instead confine any change to the
`flow_off:` path only — poll into the ring buffer using CPU time that's
otherwise spent idling in LPM during the stall, so the tuned steady-state loop
is untouched (one cheap comparison, zero cost when the ring buffer is empty,
which is the common case).

Also flagged: STM32WB09TEFX has only 64 KB RAM total (BLE stack included). The
stale comment's "4096 pairs / 137 ms" buffer size would cost 16 KB — sized down
to **2048 pairs (~68 ms, 8 KB)** instead, matching the FPGA's own ~34 ms depth
with margin, citing the sibling WB09KE bridge board's known RAM-pressure issue
as a cautionary precedent (see `project_bridge_ram.md` memory).

### 2.4 Reducing flow-off frequency (separate question, addressed but deferred)

User asked how flow-off frequency itself could be reduced. Answered with three
concrete levers, grounded in the actual config:

- **`CFG_BLE_MBLOCK_COUNT_MARGIN`** (`app_conf.h:179`, currently `54`) — the
  direct TX-pool-size knob (`CFG_BLE_MBLOCKS_COUNT = BLE_STACK_MBLOCKS_CALC(...) +
  CFG_BLE_MBLOCK_COUNT_MARGIN`). Raising it lets the tight send loop burst
  further before hitting 0x88 — doesn't raise the throughput ceiling, but makes
  individual flow-off events rarer. Costs RAM.
- **Pacing** — the tight loop currently blasts notifications until the pool is
  exhausted by design (that's what got 30k SPS). Pacing to match real per-CI
  airtime would reduce flow-off frequency but trades against that same headroom.
- **Link capacity** — DLE/ATT_MTU already maxed (`CFG_BLE_ATT_MTU_MAX=247`),
  burst-pipeline (multi-packet-per-CI) already active; shorter CI would help if
  the WB09KE bridge (central) isn't already requesting the tightest one.

Decision: defer this. Once data loss is fixed regardless of stall frequency, this
becomes a secondary optimization (less backlog, less peak buffer occupancy), not
a prerequisite. Confirmed with user: *"Yes, confirm that ordering — go ahead and
implement the ring buffer."*

## 3. Ring buffer implementation (v1 — bounded per-tick ingest)

All changes in `/data/projects/kuntur/kuntur144/mcu/kuntur-mcu/STM32_BLE/App/stream_app.c`.

Read `stream.h` (`StreamDataPacket_t`, `STREAM_PAIRS_PER_PACKET=59`) and
`fpga_spi.h` (`FPGA_SPI_ReadSamples(int16_t *samples, uint8_t n_pairs)`) to
confirm exact types/signatures before writing against them.

Added:

- **`s_ringBuf`** — `StreamPair_t s_ringBuf[2048]` (2048 pairs, 8 KB), free-running
  `s_ringHead`/`s_ringTail` indices (count = head − tail, valid across wraparound,
  power-of-2 size for cheap masking).
- **`StreamRingCount()` / `StreamRingFree()` / `StreamRingPush()` /
  `StreamRingPop()`** — the ring primitives.
- **`StreamIngestDuringStall()`** — called from the `if (s_txFlowOff)` branch
  instead of a bare `return`. Pulls one packet's worth (59 pairs) from the FPGA
  into the ring buffer per invocation, bounded and always returning (so it can't
  starve the HCI async-event task that `STREAM_APP_ResumeSending()` needs to run
  on). Riding the ~2.04 ms fallback-timer cadence measured in §1.1 keeps it
  roughly matched to the incoming 30 kSPS rate.
- **`StreamAssemblePacket()`** — replaces the direct `FPGA_SPI_ReadSamples()` call
  in the steady-state loop. Drains ring-buffer backlog first (oldest data,
  correct ordering), tops off from a live FPGA read. Empty ring buffer (common
  case) ⇒ functionally identical to the old code.
- Ring buffer indices reset on `STREAM_CONN_HANDLE_EVT` (new connection).
  Disconnect path left alone — only absorbs flow-off stalls within an active
  connection, not full disconnects (kept narrow on purpose).
- Updated the stale header comment (§2.2) and a misleading disconnect log line
  ("ring buffer will keep filling" → "sending stopped") that described the
  aspirational-but-never-built design.

## 6. Round 3 — gap-free continuous-poll diagnostic, tested: **also no improvement**

To test the "any gap causes loss" hypothesis, `StreamSendTask`'s flow-off branch
was changed to spin with zero gaps for the whole stall duration instead of
polling once per ~2 ms tick.

**Deadlock check before implementing:** spinning inside `StreamSendTask` without
returning would normally risk starving `UTIL_SEQ_Run()` from ever reaching the
HCI async-event task that calls `STREAM_APP_ResumeSending()` (which clears
`s_txFlowOff`) — the cooperative scheduler is non-preemptive between tasks.
Verified this is safe: `ble_stack.h`'s doc comment on `BLE_STACK_Tick()` states
*"The BLE Stack Tick function has to be executed to process incoming Link Layer
packets and to process Host Layers procedures. **All stack callbacks are called
by this function.**"* — meaning `ACI_GATT_TX_POOL_AVAILABLE_VSEVT_CODE →
STREAM_APP_ResumeSending()` is dispatched **synchronously** from inside
`BLE_STACK_Tick()`, which the spin loop calls every iteration. No dependency on
`UTIL_SEQ_Run()` reaching a separate task.

Implemented `StreamContinuousPollDuringStall()` behind
`#define STREAM_DIAG_CONTINUOUS_POLL_DURING_STALL` (set to `1` for this test):
poll FPGA → push ring buffer → `BLE_STACK_Tick()` → repeat, until flow resumes,
disconnect, or the ring buffer's ~68 ms capacity is exhausted (natural bound).
Build verified clean (`make -C Debug all`, only the expected pre-existing-style
warnings plus an unused-function warning for the now-bypassed
`StreamIngestDuringStall`).

## 7. The actual bug — found by re-reading the *steady-state* loop

Both experiments only modified what happens *during* a stall. Neither touched
the *transition into* one — the one piece of code untouched since before this
session:

```c
while (1)
{
    StreamDataPacket_t pkt;
    ...
    StreamAssemblePacket(pkt.samples, STREAM_PAIRS_PER_PACKET);   // pulls data OUT

    tBleStatus ret = STREAM_NotifyData(&pkt, STREAM_APP_Context.ConnectionHandle);
    if (ret == BLE_STATUS_INSUFFICIENT_RESOURCES)
      goto flow_off;                                              // pkt discarded!
    ...
}
```

`StreamAssemblePacket()` pulls 59 pairs from the FPGA/ring buffer **before**
knowing whether the send will succeed. When `STREAM_NotifyData` hits the 0x88
wall, that packet — samples already consumed, real data, correctly assembled —
was simply discarded via `goto flow_off`. `seq_num` never increments for it
(the `seq_num++` is *after* the check), so the seq_num-gap detector is
structurally blind to this loss — explaining why every recording all session
showed "0 packets lost" via seq_num while `cnt0` clearly showed otherwise. It
also explains the ~59-sample jump size (exactly one packet) and the ≈1
SKP-per-stall ratio (a one-shot event at the transition, not something that
scales with stall duration or in-stall polling strategy) — exactly why neither
Round 2 nor Round 3 could have fixed it.

### 7.1 The fix

At the `flow_off:` label, before discarding anything:

```c
flow_off:
    {
      uint32_t room = StreamRingFree();
      uint32_t n = STREAM_PAIRS_PER_PACKET;
      if (n > room)
        n = room;
      if (n > 0U)
        StreamRingPush(pkt.samples, n);
    }
    s_txFlowOff = 1U;
    ...
```

The already-assembled packet is pushed into the ring buffer instead of dropped,
so `StreamAssemblePacket()` sends it first on resume via the existing
backlog-drain logic built in §3. `STREAM_DIAG_CONTINUOUS_POLL_DURING_STALL`
reverted to `0` (bounded, scheduler-friendly, production-safe) — the diagnostic
had already answered its question; the continuous-poll function is kept in the
file for reference. Build re-verified clean.

### 7.3 Residual breakdown — two newly-characterized categories

**Category A — `+2` artifact, ~52/74 events, tiny magnitude:**
- Shows up as raw diff `-65534` in `compute_stats()`'s jump list — that's an
  unwrapped 16-bit value; true meaning is `+2` (one extra count instead of `+1`).
  Same script quirk explains why it looked identical (45–46 occurrences) across
  *every* run all session regardless of the fix — first clue it's unrelated to
  flow-off.
- Free analysis on already-recorded Run 4 data (no new firmware/recording
  needed): **52/53 events occur within 200 µs of an underrun row** (not random),
  and recur at a **strikingly regular ~2.19–2.27 s period**
  (`mean=2.1904s, std=0.2869s` across 53 events). Nothing in the reviewed MCU
  code has a ~2.2 s period — open question, possibly FPGA-side.

**Category B — scattered large residuals, ~14–21/run, magnitude 51–394:**
- Matches the ~4.4% "unexplained by flow-off" residual flagged at the very start
  of the original (pre-this-session) investigation.
- **New finding:** computed signed timing offset from each SKP to the *nearest*
  logged flow-off resume timestamp. Overwhelming majority sit at a tight
  **+46.0 to +46.2 ms offset AFTER resume** — not colocated with the resume like
  the just-fixed bug, but a fixed delay after it. This is a second, distinct
  transition bug.

  t= 83.2646s  signed_offset=+45.978 ms
  t= 85.4889s  signed_offset=+46.166 ms
