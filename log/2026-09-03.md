## 1. Where 61.44 and 227.7 both came from

Both numbers were right; they are different layers, and the spec had not
laid the chain out in one place:

| Step | Rate | Factor |
|---|---|---|
| Payload — 128 ch × 29,999.97 SPS × 16 bit | **61.44 Mbit/s** | — |
| + framing (8 B header + 4 B CRC on 256 B) | 64.32 Mbit/s | ×1.047 |
| + 8b/10b line coding | **80.40 Mbps** — coded minimum | ×1.25 |
| Yesterday's recommendation | 227.70 Mbps | **×2.83** |

The first two factors are unavoidable. The 2.83× was not.

## 2. The argument that had quietly expired

`clk`/2 was picked over `clk`/3 as "the cheapest divider." That was
written in §6.2 **before** §6.3.1 established that the *PLL* does the
dividing, off `pll0`'s existing VCO. Once that was known, the comparison
is /14 and /70 versus /21 and /105 — all four integers, all ≤ the PLL's
`O_DIV` limit of 128, all equally free. **Divider cost stopped
discriminating between the two options and nobody noticed**, because the
recommendation had already been written and was never revisited against
the finding that undermined it.

Worth naming as a pattern rather than a one-off: the spec's later section
invalidated its earlier section's reasoning, in the same document, in the
same sitting. Same shape as the `SLOT_OFFSET` bug — a document and its own
consequence never reconciled.

## 3. What the rate should be, and why

`clk`/3 = **15.1799851 MHz symbol clock → 151.799851 Mbps line rate.**

- `ECLK` = `FVCO`/21 = 75.8999256 MHz, `SCLK` = `FVCO`/105 — a clean
  **3 : 5 : 1** ratio against `clk`'s /35, still one VCO, still no second
  PLL, still no clock-domain crossing into the sampling domain.
- **506 symbol slots per sampling frame** (1518/3), 268 used, 238 spare —
  ample for `CONFIG` replication, `STATUS` and idle commas.
- Delivered 121.44 Mbit/s against 64.32 required: **1.89× headroom**.

**It is a floor, not a preference.** The next divisor down, `clk`/6, gives
253 symbol slots against the 268 a frame needs — and stays short even with
the header cut to 4 bytes and the CRC to CRC-16 (262 > 253). 1518 =
2·3·11·23, so there is nothing between 3 and 6 to try.

Decided instead on the argument that should have been made yesterday and
was not: **noise.** This is a headstage whose headline published number is
noise floor in µV RMS on a shorted input (A.3). 227.7 Mbps beside a
128-channel analog front end is 33% more switching current and radiated
field than 151.8 Mbps, carrying exactly the same payload. Headroom against
a payload that can only shrink — 128 channels is every channel the AFE
has, and A.7 step 3 expects λ **below** 30,000 SPS — is not insurance.

`clk`/2 stays documented as the step *up* if bring-up ever shows the
symbol-slot budget short. A constant change; nothing else depends on it.

## 4. Two more corrections, and the architecture simplified sharply

Later the same session, two further challenges from Manuel — both landed.

### 4.1 "Why the 8b/10b coder?"

Checked what it actually buys here, and three of its four properties turned
out to be unnecessary:

- **DC balance** — irrelevant. Verified DC coupling from the PCB: each of
  the four tunnel nets has exactly **two pads**, an FPGA ball and a
  connector pad. No series capacitor anywhere.
- **Comma / word alignment** — achievable without a line code.
- **Code-violation detection** — redundant with CRC-32.
- **Transition density** — the only real one, and needed *only* because I
  had assumed no clock pair was available.

And that assumption traced back to PLAN.md's *"tunnelled bidirectionally"*,
which was written for the transparent-bridge conception. Carried forward
without re-testing it against the ownership decision that made the upstream
diagnostics-only.

### 4.2 "I don't agree that a SPI bridge is not possible"

**He was right; my §2.1 argument was wrong.** I compared the tunnel round
trip against `tMISO` = 12 ns — an **AC parameter** (how fast the chip drives
MISO after an edge once it holds the data), not the protocol's data latency.
The RHD2164 pipeline is **two commands deep**, a fact §9.2 of the same
document already relied on. Real budget ~1333–1405 ns against a ~281–703 ns
round trip. **Latency was never the obstacle.**

Split properly:

- **Case A** (both masters execute on the real chip) — genuinely impossible,
  but by **bus saturation**: capacity 989,999 tx/s, Kuntur already uses
  989,999 (**100.0%**), Intan would add 1,050,000 → **2.06× capacity**. No
  relief: `sck` is 22.77 MHz against the chip's 24 MHz ceiling, 5.4% headroom.
- **Case B** (Intan sole master, Kuntur relays) — **feasible**. Deferred by
  Manuel on scope: it belongs to a wired-only headstage, a different product.
  Recorded in PLAN.md's V1 "Out" list with the consequence analysis, so a
  future revisit doesn't re-derive it.
- **Case C** (Kuntur master, companion emulates) — what the spec specifies,
  now argued on the correct grounds.

Worth noting *why* Case C still wins even though Case B is possible: cable
loss would be fatal to the wireless recording, and commands would cross on a
path too tight for store-and-forward CRC — the exact protection PLAN.md
asked for by name.

### 4.3 The resulting design, much simpler

Manuel's call: **both lines as Data + forwarded Clock, a synchronous link.**

| | Bidirectional draft | Synchronous link |
|---|---|---|
| Line code | 8b/10b, 25% overhead | **none** |
| Gearing | `ODDRX5` 10:1 (a symbol is 10 bits) | **`ODDRX4` 8:1, one byte per word** |
| `ECLK` | new PLL output, /21 | **`clk` itself — no new PLL output** |
| `SCLK` | new PLL output, /105 | **`ECLKDIV ÷4`** = 11.3849888 MHz |
| Line rate | 151.8 Mbps | **91.079911 Mbps** |
| Requirement | 80.40 Mbps coded min | 65.28 Mbit/s framed → **1.40×** |
| RX complexity | CDR, comma hunt, disparity | forwarded clock, fixed phase |
| Link-loss detect | data timeout | **clock absence, ~700 ns** |

The byte-oriented gearing is the quiet win: §4's frame is byte-structured,
so `ODDRX4` maps it 1:1 with no bit-packing at either end. And the earlier
"swap the pairs before the pigtail is soldered" deadline **disappears** —
both ports were already outputs; the only Kuntur change is `IO_TYPE=LVDS`
in the `.pdc`.

Also retired: my "integer symbol slots per sampling frame" constraint, which
I had treated as a requirement and built a divider ladder around. It is not
one — idle padding absorbs a fractional remainder by construction, and with
`SCLK` an integer division of `clk` the relationship is a counter, not a CDC.
That is the third self-imposed constraint this session that did not survive
being asked about.

## 5. O1 resolved — the companion-side pinout

Manuel supplied the eval-board user guide (FPGA-EB-02028-1.6). O1 is
closed, and it turned up a trap that would have cost a pigtail rework.

**Method matters here.** The PDF's schematic pages *do* annotate site
names, but `pdftotext` interleaves the multi-column schematic rows, and a
first pass produced impossible results (`FMC_CLK1_P`/`_N` landing on
`PB16B`/`PB18A`, which is not a differential pair). Rather than guess, I
built a **two-pin probe design for `LIFCL-40-9BG400C` `CABGA400` in
Radiant 2025.2.1** and read the real pad report — the same evidence class
used for the LIFCL-17 side. Table 8.1 from the guide supplied ball
numbers; the pad report supplied sites, banks and dual functions.

### What it says

- **All 34 FMC `LA` pairs plus `FMC_CLK0/1` are true differential
  `PB##A`/`PB##B` pairs**, all on **`PB` (bottom) sites**, in **banks 3, 4
  and 5**. Matches the schematic's own sheet label ("FMC-LPC (Bank3/4/5)")
  and **confirms PLAN.md A.0's claim** that FMC LPC is the bottom-bank
  connector. Not needed under decision 4 (the companion is receive-only),
  but exactly what Case B would need if the SPI bridge is revisited.
- **`VCCIO3/4/5` are fixed at 1.8 V** (Table 3.1 — no jumper, 3.3 V listed
  as N/A). Matches the Kuntur side throughout. No level mismatch to design
  around. `VADJ` (JP6/JP7/JP8, default open) feeds the mezzanine, not the
  FPGA banks.

### The trap

**FMC's `_CC` pins are not FPGA clock-capable on this board.**
`FMC_LA00_CC` (`PB56`), `FMC_LA01_CC` (`PB60`) and `FMC_LA18_CC` (`PB28`)
all lack `PCLK`. FMC's "CC" designation is about the *carrier's* clock
distribution, not the FPGA's `PCLK` capability, and Lattice did not route
them to `PCLK` pins. Taking the forwarded clock on an `_CC` pin — the
obvious move — would have put it on a pin that cannot drive a global clock
net, discovered after the pigtail was soldered.

The genuinely clock-capable pairs are `FMC_CLK0`, `FMC_CLK1`, and nine
ordinary `LA` pairs: `LA02`, `LA04`, `LA05`, `LA07`, `LA10`, `LA14`,
`LA20`, `LA24`, `LA26`.

### Recommendation

| Signal | FMC pin | Ball | Site | Bank |
|---|---|---|---|---|
| `TUN_CLK` | H7 / H8 (`FMC_LA02`) | Y2 / Y3 | `PB8A/B` | 5 |
| `TUN_DATA` | H10 / H11 (`FMC_LA04`) | V1 / W1 | `PB6A/B` | 5 |

`FMC_LA02` is the standout: alone among the eleven clock-capable pairs it
carries **`LLC_GPLL0T_IN`**, a genuine PLL *reference input*, which is
what §6.6 needs to multiply the received word clock ×4 into `ECLK`.
(`FMC_LA04`'s `LLC_GPLL0T_MFGOUT1` is a manufacturing test *output* — the
same function that appears on Kuntur's E9 and is equally unusable there.)

Both sit in bank 5, on adjacent sites (`PB6`, `PB8`), on adjacent
connector pins three positions apart in the same `H` row — which is what
matters for a hand-made pigtail, where `TUN_CLK`-to-`TUN_DATA` length
matching is the one skew a source-synchronous link actually cares about.

**Nothing desk-side now gates A.4 RTL.** O2a (does `clk` reach the
edge-clock network cleanly; is `ECLKSYNC` needed) is an implementation
detail answerable during Kuntur RTL, not a blocker.
