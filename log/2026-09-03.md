A long desk session, no hardware, across four areas — and the through-line

It began as one correction (the A.4 line rate) and ended having: measured
μ properly for the first time and set λ = 28,000 SPS; found that the
shipped 30,000 SPS silently discards 1.78% of every sample after ~12

open item; agreed a ten-mode roadmap and caught that three of its modes
would have reintroduced the exact rate bug fixed hours earlier; and swept

Net position: **A.4 has no desk-side gate left**, A.7's measurement half

## 1. Where 61.44 and 227.7 both came from

> **Superseded later the same day.** §4 removes the line code entirely and
> §6.5's λ decision rescales the result: the final figure is **85.008
> Mbps**, not the 151.8 this section lands on. Kept because the reasoning
> error it documents — an argument that expired two sections later in the
> same document — recurs in §8.


Both numbers were right; they are different layers, and the spec had not
laid the chain out in one place:

| Step | Rate | Factor |
|---|---|---|
| Payload — 128 ch × 29,999.97 SPS × 16 bit | **61.44 Mbit/s** | — |
| + framing (8 B header + 4 B CRC on 256 B) | 64.32 Mbit/s | ×1.047 |
| + 8b/10b line coding | **80.40 Mbps** — coded minimum | ×1.25 |
| Yesterday's recommendation | 227.70 Mbps | **×2.83** |

The first two factors are unavoidable. The 2.83× was not.

## 2. The argument that had quietly expired

`clk`/2 was picked over `clk`/3 as "the cheapest divider." That was
written in §6.2 **before** §6.3.1 established that the *PLL* does the
dividing, off `pll0`'s existing VCO. Once that was known, the comparison
is /14 and /70 versus /21 and /105 — all four integers, all ≤ the PLL's
`O_DIV` limit of 128, all equally free. **Divider cost stopped
discriminating between the two options and nobody noticed**, because the
recommendation had already been written and was never revisited against
the finding that undermined it.

Worth naming as a pattern rather than a one-off: the spec's later section
invalidated its earlier section's reasoning, in the same document, in the
same sitting. Same shape as the `SLOT_OFFSET` bug — a document and its own
consequence never reconciled.

## 3. What the rate should be, and why

`clk`/3 = **15.1799851 MHz symbol clock → 151.799851 Mbps line rate.**

- `ECLK` = `FVCO`/21 = 75.8999256 MHz, `SCLK` = `FVCO`/105 — a clean
  **3 : 5 : 1** ratio against `clk`'s /35, still one VCO, still no second
  PLL, still no clock-domain crossing into the sampling domain.
- **506 symbol slots per sampling frame** (1518/3), 268 used, 238 spare —
  ample for `CONFIG` replication, `STATUS` and idle commas.
- Delivered 121.44 Mbit/s against 64.32 required: **1.89× headroom**.

**It is a floor, not a preference.** The next divisor down, `clk`/6, gives
253 symbol slots against the 268 a frame needs — and stays short even with
the header cut to 4 bytes and the CRC to CRC-16 (262 > 253). 1518 =
2·3·11·23, so there is nothing between 3 and 6 to try.

Decided instead on the argument that should have been made yesterday and
was not: **noise.** This is a headstage whose headline published number is
noise floor in µV RMS on a shorted input (A.3). 227.7 Mbps beside a
128-channel analog front end is 33% more switching current and radiated
field than 151.8 Mbps, carrying exactly the same payload. Headroom against
a payload that can only shrink — 128 channels is every channel the AFE
has, and A.7 step 3 expects λ **below** 30,000 SPS — is not insurance.

`clk`/2 stays documented as the step *up* if bring-up ever shows the
symbol-slot budget short. A constant change; nothing else depends on it.

## 4. Two more corrections, and the architecture simplified sharply

Later the same session, two further challenges from Manuel — both landed.

### 4.1 "Why the 8b/10b coder?"

Checked what it actually buys here, and three of its four properties turned
out to be unnecessary:

- **DC balance** — irrelevant. Verified DC coupling from the PCB: each of
  the four tunnel nets has exactly **two pads**, an FPGA ball and a
  connector pad. No series capacitor anywhere.
- **Comma / word alignment** — achievable without a line code.
- **Code-violation detection** — redundant with CRC-32.
- **Transition density** — the only real one, and needed *only* because I
  had assumed no clock pair was available.

And that assumption traced back to PLAN.md's *"tunnelled bidirectionally"*,
which was written for the transparent-bridge conception. Carried forward
without re-testing it against the ownership decision that made the upstream
diagnostics-only.

### 4.2 "I don't agree that a SPI bridge is not possible"

**He was right; my §2.1 argument was wrong.** I compared the tunnel round
trip against `tMISO` = 12 ns — an **AC parameter** (how fast the chip drives
MISO after an edge once it holds the data), not the protocol's data latency.
The RHD2164 pipeline is **two commands deep**, a fact §9.2 of the same
document already relied on. Real budget ~1333–1405 ns against a ~281–703 ns
round trip. **Latency was never the obstacle.**

Split properly:

- **Case A** (both masters execute on the real chip) — genuinely impossible,
  but by **bus saturation**: capacity 989,999 tx/s, Kuntur already uses
  989,999 (**100.0%**), Intan would add 1,050,000 → **2.06× capacity**. No
  relief: `sck` is 22.77 MHz against the chip's 24 MHz ceiling, 5.4% headroom.
- **Case B** (Intan sole master, Kuntur relays) — **feasible**. Deferred by
  Manuel on scope: it belongs to a wired-only headstage, a different product.
  Recorded in PLAN.md's V1 "Out" list with the consequence analysis, so a
  future revisit doesn't re-derive it.
- **Case C** (Kuntur master, companion emulates) — what the spec specifies,
  now argued on the correct grounds.

Worth noting *why* Case C still wins even though Case B is possible: cable
loss would be fatal to the wireless recording, and commands would cross on a
path too tight for store-and-forward CRC — the exact protection PLAN.md
asked for by name.

### 4.3 The resulting design, much simpler

Manuel's call: **both lines as Data + forwarded Clock, a synchronous link.**

| | Bidirectional draft | Synchronous link |
|---|---|---|
| Line code | 8b/10b, 25% overhead | **none** |
| Gearing | `ODDRX5` 10:1 (a symbol is 10 bits) | **`ODDRX4` 8:1, one byte per word** |
| `ECLK` | new PLL output, /21 | **`clk` itself — no new PLL output** |
| `SCLK` | new PLL output, /105 | **`ECLKDIV ÷4`** = 11.3849888 MHz |
| Line rate | 151.8 Mbps | **91.079911 Mbps** |
| Requirement | 80.40 Mbps coded min | 65.28 Mbit/s framed → **1.40×** |
| RX complexity | CDR, comma hunt, disparity | forwarded clock, fixed phase |
| Link-loss detect | data timeout | **clock absence, ~700 ns** |

The byte-oriented gearing is the quiet win: §4's frame is byte-structured,
so `ODDRX4` maps it 1:1 with no bit-packing at either end. And the earlier
"swap the pairs before the pigtail is soldered" deadline **disappears** —
both ports were already outputs; the only Kuntur change is `IO_TYPE=LVDS`
in the `.pdc`.

Also retired: my "integer symbol slots per sampling frame" constraint, which
I had treated as a requirement and built a divider ladder around. It is not
one — idle padding absorbs a fractional remainder by construction, and with
`SCLK` an integer division of `clk` the relationship is a counter, not a CDC.
That is the third self-imposed constraint this session that did not survive
being asked about.

## 5. O1 resolved — the companion-side pinout

Manuel supplied the eval-board user guide (FPGA-EB-02028-1.6). O1 is
closed, and it turned up a trap that would have cost a pigtail rework.

**Method matters here.** The PDF's schematic pages *do* annotate site
names, but `pdftotext` interleaves the multi-column schematic rows, and a
first pass produced impossible results (`FMC_CLK1_P`/`_N` landing on
`PB16B`/`PB18A`, which is not a differential pair). Rather than guess, I
built a **two-pin probe design for `LIFCL-40-9BG400C` `CABGA400` in
Radiant 2025.2.1** and read the real pad report — the same evidence class
used for the LIFCL-17 side. Table 8.1 from the guide supplied ball
numbers; the pad report supplied sites, banks and dual functions.

### What it says

- **All 34 FMC `LA` pairs plus `FMC_CLK0/1` are true differential
  `PB##A`/`PB##B` pairs**, all on **`PB` (bottom) sites**, in **banks 3, 4
  and 5**. Matches the schematic's own sheet label ("FMC-LPC (Bank3/4/5)")
  and **confirms PLAN.md A.0's claim** that FMC LPC is the bottom-bank
  connector. Not needed under decision 4 (the companion is receive-only),
  but exactly what Case B would need if the SPI bridge is revisited.
- **`VCCIO3/4/5` are fixed at 1.8 V** (Table 3.1 — no jumper, 3.3 V listed
  as N/A). Matches the Kuntur side throughout. No level mismatch to design
  around. `VADJ` (JP6/JP7/JP8, default open) feeds the mezzanine, not the
  FPGA banks.

### The trap

**FMC's `_CC` pins are not FPGA clock-capable on this board.**
`FMC_LA00_CC` (`PB56`), `FMC_LA01_CC` (`PB60`) and `FMC_LA18_CC` (`PB28`)
all lack `PCLK`. FMC's "CC" designation is about the *carrier's* clock
distribution, not the FPGA's `PCLK` capability, and Lattice did not route
them to `PCLK` pins. Taking the forwarded clock on an `_CC` pin — the
obvious move — would have put it on a pin that cannot drive a global clock
net, discovered after the pigtail was soldered.

The genuinely clock-capable pairs are `FMC_CLK0`, `FMC_CLK1`, and nine
ordinary `LA` pairs: `LA02`, `LA04`, `LA05`, `LA07`, `LA10`, `LA14`,
`LA20`, `LA24`, `LA26`.

### Recommendation

| Signal | FMC pin | Ball | Site | Bank |
|---|---|---|---|---|
| `TUN_CLK` | H7 / H8 (`FMC_LA02`) | Y2 / Y3 | `PB8A/B` | 5 |
| `TUN_DATA` | H10 / H11 (`FMC_LA04`) | V1 / W1 | `PB6A/B` | 5 |

`FMC_LA02` is the standout: alone among the eleven clock-capable pairs it
carries **`LLC_GPLL0T_IN`**, a genuine PLL *reference input*, which is
what §6.6 needs to multiply the received word clock ×4 into `ECLK`.
(`FMC_LA04`'s `LLC_GPLL0T_MFGOUT1` is a manufacturing test *output* — the
same function that appears on Kuntur's E9 and is equally unusable there.)

Both sit in bank 5, on adjacent sites (`PB6`, `PB8`), on adjacent
connector pins three positions apart in the same `H` row — which is what
matters for a hand-made pigtail, where `TUN_CLK`-to-`TUN_DATA` length
matching is the one skew a source-synchronous link actually cares about.

**Nothing desk-side now gates A.4 RTL.** O2a (does `clk` reach the
edge-clock network cleanly; is `ECLKSYNC` needed) is an implementation
detail answerable during Kuntur RTL, not a blocker.

## 6. The SPS issue — μ measured, λ set to 28,000

"Now, I want to tackle the issue of SPS." This is A.7, and it turned out
to be answerable **now**, ahead of steps 1–2, from a recording already on
disk.

### 6.1 A recording measures both rates at once

`StreamAssemblePacket` always fills all 59 pairs — ring first, then
`FPGA_SPI_ReadSamples`, which returns the `0x8000` sentinel when `fifo0`
is empty. **The MCU sends a full packet whether or not real data exists.**
Therefore, on any recording:

- delivered rows ÷ duration = **μ**, transport capacity, independent of λ
- (rows − underruns) ÷ duration = **λ**, FPGA production

That reframing is what made the 2026-08-31 recording
(`vega_20260831_123301.csv`, 22.8 min, 40.2 M rows) a measurement
instrument rather than just a dataset. Analysed with a single streaming
`awk` pass into per-second bins — no pandas on this machine, and
`np.loadtxt` on 40 M rows is not worth the wait.

**Method caveat handled:** per-sample timestamps in the CSV are
*synthesised* (`packet_base_us + i × 1e6 // SAMPLE_RATE_HZ`,
`packet_parser.py:90`), so any rate derived from them would be circular.
Only packet-base timestamps are real RTC. Binning at 1-second granularity
makes the synthetic intra-packet stride irrelevant (a packet spans ~2 ms),
and total duration cross-checks against the sidecar's `duration_sec`.

### 6.2 Results

| | pkt/s | SPS/ch |
|---|---|---|
| **μ** transport, mean | **499.420** | 29,465.8 |
| μ at p1 / p5 | 499.00 | 29,441 |
| **λ** production (pre-retune bitstream) | 497.424 | **29,348.0** |
| margin as recorded | | 0.401% |

**682,351 packets, zero `seq_num` gaps — no packet loss at all.**

λ = 29,348.04 reproduces the spec's stated pre-retune 29,348 SPS
*exactly*, from an independent derivation. That is the check that the
method is sound, and it is why the rest of the numbers can be trusted.

**The 2026-05-15 μ = 512 pkt/s is superseded — 2.5% optimistic.**

### 6.3 The problem, quantified

Shipped λ = 30,000 SPS = 508.47 pkt/s against μ = 499.42. **ρ = 1.018.**
Not a thin margin — a sign error:

- `fifo0` (4096 pairs) fills in **7.7 s**; with the MCU ring, **11.5 s**
- thereafter **1.78% of every sample is silently discarded, uncounted**

Any recording longer than ~12 seconds made on today's firmware is missing
1.78% of its samples with nothing anywhere saying so.

### 6.4 A finding the spec did not have

The stall distribution is **bimodal**. 99.2% of seconds sit within 2
packets of peak; then there are **exactly five outlier seconds** missing
56–58 packets each — **112–116 ms stalls**, at t = 112, 232, 292, 1073,
1133 s, minimum spacing 60 s.

**The worst stall is ~116 ms, not the ~22 ms** §1.2 and B.5 both assume —
5× larger. The headstage's 208 ms of buffering does survive it (hence the
zero packet loss), but at **1.8× margin, not the ~9×** the 22 ms figure
implies. Stall duty cycle: **0.316%**.

Five events, two of them 60 s apart and another pair 60 s apart, is a
suspiciously round spacing — possibly a periodic host- or link-side event.
Noted as a lead, not a conclusion.

### 6.5 λ = 28,000 SPS/ch, and the retune

Chosen by Manuel from a table of candidates — *"we should work with the
highest data rate"* — after a first pass landed on 28,500 and a follow-up
question ("28.5 vs 28?") re-opened it. `m` = 5.23%, **16.6× the measured
stall duty cycle**; a 116 ms stall recovers in 2.2 s against the 60 s
minimum observed spacing.

The discriminator was that **μ is a bench number and in vivo it can only
get worse** — 2.4 GHz is absorbed by tissue, a surgical suite is RF-noisy,
antenna orientation moves with the animal, and BLE retransmissions reduce
effective μ directly. 28,000 tolerates μ being 5.2% worse than measured;
28,500 only 3.4%. The 1.75% of samples that buys is free.

The sampling frame is a structural constant (33 slots × 46 `clk` = 1518),
so:

```
clk_target = 28,000 x 1518 = 42.504000 MHz
```

The fractional-N model `FVCO = 32 MHz × (N_int + FRAC_N/4096)` reproduces
today's `pll0.ldc` exactly — `32 × (49 + 3315/4096)` = 1593.898438 MHz,
÷35 = 45.539955, ÷1518 = 29,999.97 — so it is trustworthy for the new
target. Expected achieved **42.5040118 MHz → 28,000.01 SPS, +0.28 ppm**
(`FVCO` 1572.648438 = 32×(49 + 595/4096), ÷37).
*(Manuel, RTL — not yet applied.)*

### 6.6 What it does not establish, and a knock-on

**It cannot verify losslessness.** FPGA overflow is invisible downstream —
discarded samples never appear, and real analog data gives no way to spot
the gap. This analysis *sets* λ; only A.7 step 1's counter can *confirm*
it. Step 1 is now the single most valuable item in A.7.

**Knock-on to A.4 §9.5**, caught before it became a surprise: the tunnel
spec assumed both sides run ≈30 kSPS differing only by crystal tolerance.
At λ = 28,000 against the Intan controller's fixed rate list (nearest
30 kSPS), the offset is a **systematic 6.67%** — one frame in fifteen, not
1 frame per 5.6 s. Fine for a visualiser, *not* fine for A2's
sample-for-sample comparison, which now genuinely depends on §10's shared
ZCHECK marker rather than merely benefiting from it. §9.5 rewritten.

Every ratio in the A.4 spec is invariant under a λ change — `ECLK` = `clk`
and the payload both scale with `clk` — so only absolute frequencies moved
(line rate 91.08 → 85.01 Mbps, `SCLK` 11.385 → 10.626 MHz). Headroom stays
1.40×, byte-slot budget stays 379.5/272.

### 6.7 Two things found while choosing the rate

**fH is set to 20 kHz — the chip maximum — so every candidate rate already
aliases.** `rhd2164_defs.vh` loads `RH1 8/0`, `RH2 4/0`, an exact match for
the RHD2000 datasheet's fH = 20 kHz row. Nyquist for that is 40 kSPS. At
28 kSPS the 14–20 kHz band folds back, and the chip's 3rd-order Butterworth
rolls off only *above* fH, so that band is essentially passband today.

28,000 vs 28,500 differs by **250 Hz of folded band against ~6 kHz already
folding** — which is exactly why the rate choice was correctly made on
transport margin alone. **The lever on signal quality is fH, not λ.**
Setting fH = 7.5 kHz (`RH1 22/0`, `RH2 23/0`, Intan's standard for spike
work) anti-aliases every rate under discussion. Raised, not yet decided;
tracked in PLAN.md A.7.

**`RL_DAC1/2/3 = 35/17/0` — flagged, then retracted.** I raised it as
matching no datasheet row. **Wrong.** Manuel identified it immediately as
the **fL = 0.50 Hz** row on p.26, and re-checking confirms it verbatim.
My `pdftotext` extraction had truncated the fL table below 1.5 Hz, and I
generalised from a partial table instead of noticing the truncation. fL is
unchanged and was always correct.

### 6.8 25,000 SPS as a wired-mode bring-up step

Manuel: *"For initial work with wired mode, we can start with 25 kSPS, but
the goal is to make it work with 28 kSPS."*

25,000 is the only candidate landing **exactly** on an Intan-selectable
rate (`clk` = 37.95 MHz, +0.00 ppm — an exact PLL solution). That collapses
A.4 §9.5's systematic offset to crystal tolerance alone, so the first
dual-path work has no rate artifact that could be mistaken for a link bug.
Production stays 28,000; every ratio in the tunnel spec is invariant
between the two rates, so only absolute frequencies move.

### 6.9 fH lowered to 7.5 kHz — and every prior recording was aliased

Manuel's call, applied the same session to
`kuntur/.../afe/rhd2164/rhd2164_defs.vh`:

```
RHD_RH1_DAC1  6'd8  -> 6'd22      RHD_RH2_DAC1  6'd4  -> 6'd23
RHD_RH1_DAC2  5'd0     unchanged  RHD_RH2_DAC2  5'd0     unchanged
```

Both the old and new values are verbatim datasheet rows (p.26): 20 kHz was
`8/0, 4/0`; 7.5 kHz is `22/0, 23/0`.

**The finding behind it is uncomfortable and worth stating plainly:** fH
sat at the chip's *maximum* 20 kHz, whose Nyquist is 40 kSPS. This project
has never sampled above 30 kSPS. So on every recording ever made here, the
14–20 kHz band folded back into the signal — and because the RHD2000's
3rd-order Butterworth rolls off only *above* fH, that band was essentially
passband, not attenuated. At 28 kSPS with fH = 7.5 kHz, Nyquist (14 kHz)
now sits well clear of the corner and the path is properly anti-aliased
for the first time.

**Not a noise fix.** I nearly claimed a ~39% noise improvement from
√(20/7.5) before checking: the datasheet specifies `vni` = 2.4 µVrms and
notes it *"varies slightly (< 15%) with amplifier bandwidth"*. The naive
bandwidth-scaling argument does not apply to this amplifier. A.3's
headline noise-floor number should not be expected to move much.

**Requires an FPGA rebuild and reflash** — these are baked into
`regbank.v`'s power-up configuration table. Pair it with the PLL retune
(§6.5) so one rebuild covers both.

Also worth noting for A.6.5: the sidecar's `filter_settings.registers`
will now report the new values, so any recording made after the reflash
carries its own proof of which bandwidth it used — which is exactly the
provenance that would have caught this years earlier.

### 6.10 A note on how the fL false alarm happened

Worth recording as a method lesson rather than buried. I extracted the
datasheet's fL table with `pdftotext`, saw `RL_DAC2` values of 0–4 across
every visible row, and concluded 17 matched nothing. The extraction had
silently truncated the table below 1.5 Hz — the 0.50 Hz row was right
there, three lines further down.

The error shape is the same one this project keeps hitting: **generalising
from a partial view without checking whether the view was complete.**
Cheap to avoid — I had the page and could have printed more of it. The
same instinct that made me rebuild the LIFCL-40 pad report rather than
trust a mangled schematic extraction should have applied here and didn't.

## 7. Operating-mode roadmap — agreed, after an arithmetic check that mattered

Manuel proposed a ten-mode roadmap to inform future decisions: Mode 0 for
the animal test, Modes 0–4 for public release, 5–9 future. Written into
`stream-packet-format.md` §5.3 (which is where `mode_id` points), and
summarised in PLAN.md's V1 scope.

Checking it against the **new** budget found one real problem and one
structural simplification.

### 7.1 Modes 2–4 reintroduce the bug A.7 just fixed

At λ = 28,000 with `m` = 5.23%, the aggregate budget is **56,000
samples/s at 16 bit** (112,000 B/s, 474.58 pkt/s). Modes 0 and 1 hit it
exactly. Modes 2–4 as proposed (8×7,500, 16×3,750, 32×1,875) all come to
**60,000** — the *pre-A.7* budget from PLAN.md's "~60 kSPS aggregate"
line, which was right at λ = 30,000 and is not at 28,000.

That puts them at 107.1% of budget and **`m` = −1.78%** — numerically the
identical ρ > 1 failure diagnosed in §6.3 of this log. Worth noting how it
arose: the mode table was written against a budget figure that had been
correct for months and silently stopped being correct four hours earlier.

### 7.2 The fix and the simplification are the same move

The RHD2164 pair converts **all 128 channels every frame** at F = 28,000.
So a mode is "pick N channels, deliver each every k-th frame", per-channel
rate F/k — and **k must be an integer** or samples are non-uniformly
spaced, which no downstream analysis can undo.

Checked against that, only Modes 0 and 1 were integer (k = 1, 2). Modes
2–4 gave k = 3.733 / 7.467 / 14.933; Modes 5–8 gave 1.12 / 2.24 / 4.48 /
26.92.

Correcting Modes 2–4 to **7,000 / 3,500 / 1,750** fixes budget and
uniformity together, because both had the same cause. The whole 16-bit
family then becomes k = 1, 2, 4, 8, 16 — **one clock, one frame rate, a
power-of-two decimation counter**. No per-mode PLL config, no per-mode
rate to measure or record, mode switching is a counter reload. It extends
free to 64 ch @ 875 and 128 ch @ 437.5, which the proposal didn't reach.

The 12-bit family fits the same frame at k = 3, 6, 9, 12, 24, 27, 48 →
N = 8, 16, 24, 32, 64, 72, 128. **Mode 8's 72 channels lands almost
exactly**: k = 27 gives 1,037.0 SPS against the proposed 1,040. Modes 5–7
(3/6/12 ch) have no integer k — 3 ch at k = 1 is 84,000 aggregate,
`m` = −6.46%. If those channel counts are wanted specifically they need
their own frame rate (F = 25,000 is an exact PLL solution and gives
`m` = +4.77%). **Channel counts are the free parameter, not the rates.**

### 7.3 Three things the later modes need that 0–4 do not

- **12-bit breaks §4's payload contract.** 236 B = 1888 bits = 157.33
  samples, so either 157 fit with 4 bits spare (0.2% waste, keeps "never
  split a sample") or samples straddle packets at bit level. Take the
  former; amend §4 before any 12-bit mode ships.
- **Mode 9 is not a sample stream.** Spike times are events:
  `sample_index` and `payload_samples` don't apply, it needs its own
  `frame_type`, and — the real issue — its **bandwidth is data-dependent**,
  so §1.3's λ < μ stops being a static check. Needs a worst-case firing
  rate or an explicit rate limiter with documented overflow behaviour.
- **`mode_id` 0 is reserved** in the existing spec so an all-zeros header
  can't masquerade as a valid mode (same discipline as §4 rule 4).
  Recommended keeping that and shifting the proposal to wire values 1–10,
  with "Mode 0" surviving as the prose name for the current 2ch mode.

Also flagged: `ch_sel` has a 4-way mux serving 2 channels today. N = 32 or
128 is a different structure, and B.3 already wants `ch_sel` decoupled
into a generic `{channel, sample, valid}` source. Modes 0–4 are the
natural forcing function for that refactor.

### 7.4 Agreed table — and it needs no third clock

Manuel accepted the Modes 3–5 correction, took the separate-PLL route for
the 12-bit modes, asked for spike-times to be spec'd as a placeholder
only, and renumbered everything to **Modes 1–10** (leaving `mode_id` 0
reserved for *unknown*, which preserves the property that an all-zeros
header cannot pose as a valid mode).

The result is tidier than either of us expected going in:

| Family | Modes | F | `clk` | k | aggregate | `m` |
|---|---|---|---|---|---|---|
| 16-bit | 1–5 | 28,000 | 42.504 MHz | 1, 2, 4, 8, 16 | 56,000 smp/s | +5.23% |
| 12-bit | 6–9 | 25,000 | 37.950 MHz | 1, 2, 4, 24 | 75,000 smp/s | +4.77% |

**No third clock is needed anywhere in the system.** 42.504 MHz is A.7's
production retune; 37.95 MHz is the *exact* PLL solution already specified
as A.4's wired-mode bring-up rate (§6.8). The two uses coincide by
accident and now justify each other.

Mode 9's 72 channels resolve to k = 24 → **1,041.67 SPS**, against the
proposed 1,040 — and that lands the whole 12-bit family on exactly 75,000
aggregate.

Packet rate across all nine sample-stream modes spans **474.58–476.69
pkt/s, a 0.45% spread**, so §5.2's central claim — one `μ_low`
measurement covers every mode, B.4 characterisation does not multiply by
mode count — survives the introduction of a second frame rate.

**Runtime family switching** needs a second clock source and a glitch-free
mux, and the hardware has exactly that spare: `.mrp` reports **PLLs 1 of
2** and **DCSs 0 of 1**. One free PLL for 37.95 MHz, one dynamic
clock-select — which is what DCS is for. Not needed for v1 in any case,
since Modes 1–5 all share F = 28,000.

### 7.5 Mode 10 recorded as a placeholder, with its three problems named

Spec'd, not designed, per Manuel. What is written down is why it is not
just another table row:

1. **§4's payload contract does not apply** — `sample_index` and
   `payload_samples` are meaningless for an event stream; it needs its own
   `frame_type`.
2. **Its bandwidth is data-dependent**, so **§1.3's λ < μ stops being a
   static check**. Needs a worst-case firing-rate assumption written down,
   or an explicit rate limiter with documented overflow behaviour. Silent
   loss during a burst — a seizure, a stimulation artifact — is precisely
   the failure this spec exists to prevent, and it is the one mode where
   the existing invariant does not protect against it.
3. **No per-sample timestamp to inherit** — event times need their own
   encoding and resolution decision.

### 7.6 Carried consequences for Modes 2–5

- **12-bit packing needs a §4 amendment** (157 samples + 4 spare bits per
  packet, preserving "never split a sample"). Not needed for Modes 1–5.
- **`ch_sel` must be restructured for N > 2** — it has a 4-way mux serving
  2 channels today. Modes 2–5 are the forcing function for B.3's
  already-flagged decoupling into a generic `{channel, sample, valid}`
  source.
- **`SET_CHANNELS` carries two channel indices today** and needs to carry
  N, or be replaced by a channel-set descriptor. That is a control-plane
  change belonging in `channel-selection-control-plane.md`, not here.

## 8. Stale-arithmetic sweep of `stream-packet-format.md`

Prompted by a question from Manuel — *"why is mode_id 0 reserved?"* —
which turned into a check of whether other numbers in the spec had been
invalidated by the λ change the same way Modes 3–5 were.

**On the question itself:** it is §3.2, and the spec's stated reason is
narrower than the one I had been giving. §3.2 says a receiver seeing
`mode_id = 0` "must refuse to decode rather than assume 2 channels" — the
argument is about *defaulting*, not about corruption. Without a reserved
value a receiver has to guess, and the natural guess is the legacy
2-channel mode, which mis-decodes an N-channel stream into
plausible-looking waveforms with every sample on the wrong channel.

The all-zeros framing I had attached to it is a real secondary benefit but
was **my addition, not the spec's** — worth separating, and now separated
in §5.3. It carries more weight here than it normally would because §3.5
deliberately puts no CRC on this header, and the exposed bridge→PC UART
hop has none either yet (deferred to B.2) on a link known since
2026-08-06 to drop bytes at 2 Mbaud.

**Five stale spots found and fixed**, all invalidated by λ 30,000 →
28,000 and by μ 512 → 499.42:

| § | Was | Now |
|---|---|---|
| 3 | header budget vs 120,000 B/s, "508.5 pkt/s", *"the header cannot grow"* | 112,000 B/s, 474.58 pkt/s, **24.8 pkt/s of slack ≈ 12 header bytes** |
| 3.1 | wrap `2³²/60,000` = 19.9 h | **21.3 h** (16-bit) / **15.9 h** (12-bit) — mode-dependent |
| 3.3 | `T_fill` table topped at 60,000 smp/s | 75,000 and 56,000 rows added |
| 6.3 | telemetry cadence vs "508.5 pkt/s" | 474.6 pkt/s |
| 5.3 | cited §4 rule 4 for the reservation | cites §3.2, the actual rationale |

The §3 one is the most consequential and cuts against the spec's own
conclusion: **the header is no longer against a wall.** It was written
when demand (508.5) sat 3.5 pkt/s below a believed 512 ceiling. Lowering λ
bought header room as a side effect — about twelve bytes' worth. That is
not free space (it *is* the margin §1.3 requires, so a header byte costs
~0.45 percentage points of it), but "the header cannot grow" is no longer
true, and left uncorrected it would have silently blocked a future design
decision on obsolete arithmetic.

Two decision records in §10 and the header status block were annotated
rather than rewritten: both were taken against numbers that have since
moved, both decisions still stand, and saying so is more useful than
either leaving the stale figure or quietly swapping it.

**The pattern is worth naming.** Three times today a number that had been
correct for months quietly stopped being correct: the 60,000 aggregate in
the mode proposal, the 120,000/512 pair in the header budget, and the
19.9 h wrap. All three descend from the same root — λ — and none of them
were flagged by anything, because nothing links a derived figure back to
its input. That is a documentation-structure weakness, not a one-off, and
it belongs with B.1's ground-truth audit.
