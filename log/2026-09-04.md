Two things in the agreed spec turned out to be wrong or missing once code
had to exist, and both were closed in `stream-packet-format.md` before
anything was written:

1. The frame had **no way to say "the FPGA counter could not be read"** —
   only "it read zero". That is the state the system is actually in, and
   will stay in until step 1's RTL lands.
2. §6.4's "no new mechanism, just a regbank read" was true about the
   *primitive* and false about the **calling context**: every regbank
   access in this firmware is structurally confined to streaming being
   *stopped*, and a 1 Hz telemetry read is the first thing to want it
   mid-stream.

Neither is a large change. Both are the kind that is nearly free before
code and expensive after.

## 2. The frame could not say "not measured"

§6.2 as agreed had byte 1 as `reserved, must be 0`, and the two FPGA
fields as plain `uint32`/`uint16`.

That gives the FPGA counters two expressible states — zero, and non-zero
— for **three** real ones. The third is *"this build cannot read them"*,
which is not an edge case: it is what is true today, and stays true for
as long as A.7 step 1 is unbuilt.

Reporting it as `0` breaks the frame's own reason for existing. §7's
attribution table opens with "`fifo0_overflow_samples` moved → producer-
side loss"; with a silent zero, *did not move* and *cannot be read* are
the same bytes. And §6.3 already forbids exactly this shape one level up
— "a receiver must not infer that 'no telemetry frame yet' means 'no loss
yet'" — without noticing that the same trap sits inside the frame.

**Resolution:** byte 1 is now `flags`, bit 0 `fpga_counters_valid`. Same
frame size, every other offset unchanged, no `telemetry_version` bump
needed. When the bit is clear, both `fifo0_*` fields are transmitted as 0
and a receiver must not display or accumulate them — the pc-app shows
`n/a (no RTL counter)`, in grey, rather than a green zero.

This is the cheapest possible version of a fix that would have cost a
version bump if it had been found after the first frame shipped.

## 3. The regbank-read invariant §6.4 walked past

§6.4: *"The MCU reads them over the existing `REG_READ16` path that
A.1.1g already generalised — no new mechanism, just a counter and two
words."*

True about the primitive. But `fpga_spi.h` states the calling rule
explicitly:

> never interleaved with an in-progress `FPGA_SPI_ReadSamples()`.
> **Structural as built** — `0xFFF1` rejects these unless streaming is
> already stopped, and they execute from `StreamSendTask`'s stopped
> branch.

Every regbank access built so far — `SET_CHANNELS`, `REG_READ16`,
`REG_WRITE16`, `stream_enable` — obeys that by construction, and the
control-plane spec's whole §5 exists because an earlier inline placement
hung the MCU. A 1 Hz telemetry read while streaming is the first thing
that wants to violate it, and the agreed text does not mention that it
does.

**It is nonetheless safe, but only from one place, and that is worth
writing down rather than discovering.** The operative clause is
*interleaved with an in-progress read* — a bit-banged SPI0 sequence has
no preemption to interleave *within*, so what is really forbidden is
issuing from a context that can land mid-sequence: a BLE callback, an
ISR, or a state where a POP pair is left half-open. None apply at the top
of `StreamSendTask`'s send path: it is a packet boundary, A.1.1g's
trailing NOP already guarantees a clean FSM there (the same property
`StreamFlushFpgaFifo` relies on), and no command is in flight.

New §6.6 records this as three rules rather than a hope:

1. **Reads only, never writes.**
2. **From `StreamSendTask` only, at a packet boundary** — never from the
   `0xFFF1` callback, a timer, or the flow-off branch. The flow-off
   branch matters specifically: `fifo0` is under maximum pressure there,
   the worst possible moment to spend SPI0 time on anything but popping
   it.
3. **Skipped, not deferred, when the moment is wrong.** A stall that
   keeps the send loop away for a second costs that second's frame.
   Counters are cumulative, so the next frame carries everything the lost
   one would have.

Cost: three 2-transfer reads at ~10 µs/transfer ≈ **60 µs per second**,
0.006% of the send loop, three orders of magnitude inside `m` = 5.23%.
That is why the cadence is 1 Hz and not faster.

The read is not enabled in this build — `STREAM_TELEMETRY_FPGA_COUNTERS`
is `0` and the two word addresses are placeholders, because step 1's RTL
does not exist. Turning it on is that switch plus the addresses, and
nothing else in the chain changes, so the chain does not need re-testing
when step 1 lands.

## 4. §6.5 named a discard site that is not one

§6.5 listed two places where the MCU silently discards:

- the `flow_off:` path's clamped ring push, and
- `StreamContinuousPollDuringStall` (`:826-835`), "the same clamp shape".

Only the first is real. The second — and `StreamIngestDuringStall`, which
has the identical shape — clamps its FPGA **read**:

```c
uint32_t room = StreamRingFree();
uint32_t n = STREAM_PAIRS_PER_PACKET;
if (n > room) n = room;
FPGA_SPI_ReadSamples(tmp, n);   /* reads n, pushes n */
StreamRingPush(tmp, n);
```

A short read leaves the remainder in `fifo0`. That is the intended
backpressure, working — the thing §6.5's own closing paragraph says about
the rest of the headstage ("a full MCU ring stops `StreamIngestDuringStall`,
which pushes pressure back onto `fifo0` rather than dropping").

The `flow_off:` clamp looks the same and is not, because there the 59
pairs are **already out of the FIFO** when the notify fails; whatever
does not fit exists nowhere else. There is exactly one MCU-side discard
site, `ring_truncated_samples` counts it, and the spec now says so.

## 5. Two implementation choices worth recording

**Stall time is accumulated through a microsecond remainder, not by
dividing each stall.** At ~133 flow-offs/s, most resolving well under a
millisecond, `s_stall_time_ms_total += stall_us / 1000` truncates almost
every one to zero and reports a duty cycle of approximately nothing —
confidently, and in the one number step 3b exists to measure. Carrying a
`s_stall_us_remainder` costs one `uint32` and is exact.

**Loss is computed by differencing consecutive frames, not by comparing
totals.** §6.7 (new) records why this is worth doing under v0 at all: the
pc-app can count the same aggregate the MCU's `anchor_sample_index`
counts (2 per pair), and the shortfall between them over an interval
**is** the whole-path sample loss — available now, without the v1 header,
and independent of `seq_num`, which counts only packets and cannot see a
short packet or a truncated frame.

Differencing rather than absolute comparison is what makes it robust: a
counter reset on the far end (`START_STREAMING`, a reconnect) appears as
an implausible delta and the interval is skipped, so **no reset has to be
tracked on the pc-app side at all.** Tested, including the reset case.

## 6. What is verified, and what is not

Desk-verified: §6.2's byte offsets (the test builds a frame field by field
from the spec table with every value distinct, so a swapped pair cannot
pass), the three-way magic dispatch through the real `SerialReader`
thread over a pty with leading garbage, forward-compatibility with a
longer future frame (bridge fields read from the **end**, which is why
they are read that way), the `fpga_counters_valid` distinction, and the
loss arithmetic across a far-end reset.

**Not verified, needs the bench:**

1. **The bridge connection sequence with a fourth CCCD.** §9 called this
   the riskiest part and nothing here changes that assessment — it has a
   history of fragility and no desk test can reach it. Bring it up
   against a headstage that is *already streaming*, so a telemetry
   failure is unambiguous rather than tangled into a stream that never
   started.
2. **The 1 Hz notify's real cost on packet rate.** Argued negligible in
   §6.6, but `μ` was measured without it. A before/after comparison is
   nearly free in the same session.
3. **`fifo0_overflow_samples` end to end** — blocked on step 1's RTL by
   construction.

All three fold into the FPGA rebuild + reflash session that item 1 of the
critical path already requires.
