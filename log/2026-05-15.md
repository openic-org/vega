# 2026-05-15 — Session Log

## Summary

Replaced the ring-buffer + TIM2/ISR architecture with a synchronous SPI pull inside
the BLE tight loop, then doubled SYSCLK from 32 MHz to 64 MHz. End-to-end result:
**~1 000 kbit/s, 30 215 SPS** — the 30 kSPS target achieved.

---

## 1. Architecture: synchronous SPI pull inside the BLE tight loop

**Previous design:** TIM2 ISR at 60 kHz incremented `s_samples_pending`; a UTIL_SEQ
task drained it via bit-bang SPI into a 16 KB ring buffer (4 096 pairs); `StreamSendTask`
read from the ring buffer when it had ≥ 59 pairs.

**Problem:** Multiple layers of indirection (timer → ISR → task → ring buffer → BLE task)
added latency and complexity without adding throughput. The ring buffer consumed 16 KB of
the 64 KB RAM. The UTIL_SEQ task-starvation bug (Stage 4) showed that two tasks sharing
the same priority level caused unpredictable scheduling.

**New design:** `FPGA_SPI_ReadSamples()` called directly inside `StreamSendTask`'s tight
loop, immediately before `STREAM_NotifyData()`. One call per BLE notification, 59 pairs
per call. TIM2, its ISR, the ring buffer, and the FPGA_SPI_Task are removed entirely.

```c
/* Inside StreamSendTask tight loop — one iteration = one BLE packet */
FPGA_SPI_ReadSamples(pkt.samples, STREAM_PAIRS_PER_PACKET);  /* 59 pairs via SPI */
tBleStatus ret = STREAM_NotifyData(&pkt, conn_handle);
```

**Why this works:** The tight loop already serialises everything. Each iteration consumes
exactly what one BLE packet needs. No timer, no intermediate buffer, and no synchronisation
primitives are required on the MCU. Buffering responsibility moves entirely to the FPGA
FIFO (≥ 256 pairs recommended to cover the ~7.5 ms connection interval).

**Why 32-bit SPI words don't help for bit-bang:** Total SCK cycles = total bits.
118 × 16-bit transfers = 59 × 32-bit transfers = 1 888 bit operations either way. The
only saving from 32-bit is 59 fewer NSS toggle pairs ≈ 4 µs/packet — negligible. (32-bit
packing is a real win only for hardware SPI, where per-transfer setup overhead dominates.
Hardware SPI3 is on APB1 and is permanently gated by the BLE radio.)

**Files changed:**

| File | Change |
|---|---|
| `Core/Src/fpga_spi.c` | Removed TIM2/ISR/task; added `FPGA_SPI_ReadSamples()` |
| `Core/Inc/fpga_spi.h` | Slim header — only `Init` and `ReadSamples` |
| `STM32_BLE/App/stream_app.c` | Removed ring buffer, simulation sawtooth, `STREAM_APP_IngestSamples()`; call `FPGA_SPI_ReadSamples()` in tight loop |
| `STM32_BLE/App/stream_app.h` | Removed `STREAM_RING_BUFFER_PAIRS`, `STREAM_APP_IngestSamples` |
| `Core/Src/stm32wb0x_it.c` | Removed `TIM2_IRQHandler` |

**Commit:** `c882f5b` — "fpga_spi: sync SPI pull inside BLE tight loop; remove ring buffer + simulation"

**Result at 32 MHz:** 827.8 kbit/s, 424 pkt/s, **25 020 SPS**.

## 2. Loop unrolling in `spi_bb_transfer`

**Change:** Replaced the 16-iteration bit loop with a fully unrolled macro expansion —
each bit position is a compile-time constant, so the loop counter, decrement, branch, and
variable shift are all eliminated.

```c
#define SPI_BIT(n) \
    if (tx & (1U << (n))) MOSI_HIGH(); else MOSI_LOW(); \
    SCK_HIGH(); \
    if (MISO_READ()) rx |= (uint16_t)(1U << (n)); \
    SCK_LOW()

/* Fully unrolled — no loop, no variable shift */
SPI_BIT(15); SPI_BIT(14); ... SPI_BIT(0);
```

**Result:** 813 → 825 kbit/s (+1.5%). Small gain because at O2 on Cortex-M0+ the compiler
was already near the C ceiling (~10–11 cycles/bit). Assembly would reach ~4 cycles/bit but
was not needed once the clock was doubled.

## 3. SYSCLK 32 → 64 MHz

**Motivation:** The bit-bang SPI is pure APB0 GPIO — its speed scales directly with SYSCLK.
RC64MPLL was already running at 64 MHz; SYSCLK was using the /2 divider. Removing the
divider doubles the SPI clock for free.

**Change:** Two lines in `SystemClock_Config()` in `Core/Src/main.c`:

```c
/* Before */
RCC_ClkInitStruct.SYSCLKDivider = RCC_RC64MPLL_DIV2;
HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_WAIT_STATES_0);

/* After */
RCC_ClkInitStruct.SYSCLKDivider = RCC_RC64MPLL_DIV1;   /* 64 MHz SYSCLK */
HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_WAIT_STATES_1);
```

**Why this is safe:**

| Subsystem | Clock source | Effect of SYSCLK change |
|---|---|---|
| BLE radio | 32 MHz HSE RF (dedicated) | None — completely independent |
| SMPS | RC64MPLL / 4 = 16 MHz | None — derived before the SYSCLK divider |
| UART 115 200 baud | PCLK (recalculated by HAL at init) | Auto-corrects — MX_USART1_UART_Init runs after SystemClock_Config |
| Flash | AHB | Needs 1 wait state at 64 MHz; was 0 at 32 MHz |

**Commit:** `16a80b6` — "mcu: bump SYSCLK 32→64 MHz (RC64MPLL/DIV1, FLASH_WAIT_STATES_1)"

## 4. End-to-end throughput

Benchmark file: `pc-app/bench_20260515_122843.csv` — captured both firmware versions in
a single continuous run (32 MHz for ~80 min, then reflash at 64 MHz).

| Metric | 32 MHz | 64 MHz |
|---|---|---|
| kbit/s | 827.8 | **999.7** |
| packets/s | 424 | **512** |
| SPS | 25 020 | **30 215** |
| Target (30 kSPS) | ✗ | **✓** |

**Why the speedup is 1.21× and not 2×:**
Only the SPI fraction of the per-packet cycle benefits from the faster clock. The BLE stack
time (~1.81 ms/packet) runs on the radio's 32 MHz HSE and is unchanged.

```
32 MHz:  SPI ~590 µs  +  BLE ~1.81 ms  =  ~2.40 ms/packet  →  25 020 SPS
64 MHz:  SPI ~295 µs  +  BLE ~1.81 ms  =  ~2.10 ms/packet  →  30 215 SPS
```

| 1 — Startup & BLE Connection | POWER ON → clock init → peripheral init → advertising → connect → DLE → PHY 2M → CCCD write → VTIMER armed |
| 2 — FPGA SPI Acquisition | `StreamSendTask` tight loop → header build → `FPGA_SPI_ReadSamples` → `spi_bb_transfer` internals (APB0 only) |
| 3 — BLE Send & Flow Control | `STREAM_NotifyData` → `aci_gatt_srv_notify` → `0x88` flow-off → `TX_POOL_AVAILABLE` → `ResumeSending` → restart |

**Design notes surfaced:**
- PHY upgrade (`hci_le_set_phy`) has no retry in the firmware; if the peer declines 2M the
  stack proceeds with 1M and continues to the CCCD wait unchanged.
- The bit-bang `spi_bb_transfer` is compiled at GCC `-O2` (instruction scheduling + inlining).
  The `SPI_BIT` macro is expanded 16 times inline — no loop counter, no branch, no variable
  shift — so the compiler emits the tightest possible straight-line GPIO toggle sequence.

## 6. BLE testing infrastructure

### `pc-app/test_validator.py`

Headless regression harness that reads live frames from the WB09KE bridge and
reports every second:

| Column | Description |
|---|---|
| `Elapsed` | Seconds since start |
| `pkt/s` | Packets per second in the last interval |
| `SPS` | Sample pairs per second (pkt/s × 59) |
| `drops/s` | `seq_num` gaps in the last interval |
| `framing` | Junk bytes discarded before 0xAA 0x55 re-sync |
| `ts_err` | Cumulative raw timestamp backwards-jumps (pre-clamp) |

Exit code 0 = PASS, 1 = FAIL (drops > `--max-drops` or serial error).

```bash
python test_validator.py --port /dev/ttyACM0                        # run until Ctrl-C
python test_validator.py --port /dev/ttyACM0 --duration 60 --max-drops 0
python test_validator.py --port /dev/ttyACM0 --verbose              # inline drop detail
```

## 8. Remove `.ioc` files

`kuntur-mcu.ioc` deleted from the Kuntur MCU repo (commit `a8e726e`). The WB09KE
bridge never had one.

**Rationale:** the `.ioc` is not used by the build system (STM32CubeIDE uses
`.cproject`/`.project`). Its only function was to enable CubeMX code regeneration,
which silently resets the manually-tuned settings documented in the CubeMX
regeneration checklists. Keeping the file was a latent footgun.

## 9. Open questions for FPGA design

When the MCU reads 59 pairs synchronously and the FPGA FIFO is empty (MCU consuming
faster than FPGA producing), the FPGA needs a defined underrun response. Options:

1. **Return zeros** — simple; MCU gets silence.
2. **Return a sentinel word** (e.g. `0xFFFF`) — MCU can detect and substitute last sample.
3. **FIFO-empty flag pin** — MCU checks a GPIO before each burst; skips SPI if empty.

The FPGA FIFO must be ≥ 256 pairs deep to absorb the ~7.5 ms connection interval at
30 kSPS (225 pairs/CI). A 256-deep FIFO is the minimum safe size.
