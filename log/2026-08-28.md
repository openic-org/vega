## 2. What drawing it found

All six came out of reading source to draw it, none from looking for
bugs.

1. **The bit-bang pins are on AHB, not APB0.** `fpga_spi.h`/`.c` said
   "all pins on APB0 — never gated by BLE radio", repeated in
   `stream_app.c`, `cpu_bench.c` and `gpio_bench.h`, and in
   `memory/project_fpga_spi_driver.md` (which also carried invented
   addresses, `0x40001000`/`0x40001400`). Per `stm32wb09.h` — the project
   builds `-DSTM32WB09` — GPIOA/GPIOB are on **AHB**: `AHBPERIPH_BASE`
   (`0x48000000`/`0x48100000`), `RCC_AHBENR_GPIOAEN`/`GPIOBEN`. APB0 at
   `0x40000000` carries RTC, SYSCFG, TIM2/16/17 and WDG, no GPIO. The
   conclusion is unaffected and slightly stronger — the pins aren't on
   the stalling APB, nor on any APB — but "APB0" matches nothing in the
   reference manual. Fixed in all five comments and in the memory note,
   which now carries a dated correction and a full four-bus map.
2. **`0xFFF3` was undocumented.** CLAUDE.md listed only `0xFFF1`
   ("reserved") and `0xFFF2`. The service has a third characteristic
   carrying every command response. CLAUDE.md now has a *Control plane*
   section: five opcodes with lengths and their streaming-stopped
   requirement, the three response shapes, and the two invariants a
   reader would otherwise have to reconstruct from `stream_app.c` —
   commands are deferred out of the BLE callback, and `STOP_STREAMING`
   disables ingestion *before* flushing.
3. **CLAUDE.md's streaming pipeline was fiction in three places.** Ring
   size 4096/137 ms (really 2048/68 ms); a simulation-vs-real branch that
   no longer exists; and `STREAM_APP_IngestSamples()` called "from the
   SPI DMA completion handler" — no such function, no such ISR. Sample
   flow is a synchronous bit-bang pull from `StreamSendTask`, and the
   ring is a stall backlog that is empty in steady state. Also corrected
   `BLEStack_Process_Schedule()` to the `BLE_STACK_Tick()` the
   WB09KE_HF loop actually calls.
4. **`CFG_TASK_FPGA_SPI_ID` was dead** — nothing registered or set it
   since TIM2/SPI3/`FPGA_SPI_Task` were removed. Removed. Worth noting
   why it wasn't left inert: the 2026-05-10 starvation bug turned on this
   enumerator's ordering against `CFG_TASK_STREAM_SEND_ID`, and that
   ordering fix is no longer in place (`STREAM_SEND` precedes it again) —
   harmless with no task using the ID, a trap the moment one does.
5. **The bridge's TX ring truncates frames silently.** `VEGA_UART_Write()`
   drops the remainder of a write when the 4096-byte ring is full, which
   puts a short frame on the wire; the pc-app resyncs on the next magic
   pair and books it as a missing packet. So a USB-side backlog and a
   radio problem have been reading identically in `dropped_packets` this
   whole time, and the bridge — the only place that can tell them apart —
   wasn't looking. Added `s_drop_bytes`/`s_drop_frames`, incremented
   under a short critical section on the drop path only. Not reported
   anywhere yet, deliberately: the debug console is a no-op by default
   and shares the wire with the data stream, and a new bridge→PC frame is
   a cross-boundary interface, so it gets a spec first. New B.5 item with
   the proposed `0xDD 0x22` shape.
6. **The bridge ring is single-producer by assumption, not
   construction.** `vega_uart.c` documents itself as main-context-only,
   but `USART1_IRQHandler`'s ORE branch reaches `VEGA_UART_Write` through
   `DT_INFO_MSG`. Inert only because `CFG_DEBUG_APP_TRACE` is `0`. The
   trap is its shape: the configuration you'd enable to debug a streaming
   problem is the one that can corrupt the stream, and the damage
   presents as a framing error, not a tracing bug. New B.5 item, not

## 3. Full-system timing, derived

The Signal Chain page needed real numbers, so the rates were derived and
checked rather than sketched:

```
30 000 SPS / 59 pairs        =  508.5 packets/s
                             /  133.3 intervals/s  =  3.81 packets per CI
248 B x 10 bits / 2 Mbaud    =  1.24 ms airtime  ->  4.73 ms of every 7.5 ms
126 102 / 200 000 B/s        =  63.1 % UART utilisation
225 pairs produced per CI    =  225 popped; fifo0 teeth are 5.8 % of capacity
```

Two structural facts read straight off the lanes. **Every buffer in the
chain runs nearly empty** — 123 ms of elastic storage exists between
amplifier and PC (fifo0 34 ms, MCU ring 68 ms, bridge ring 20.5 ms) and
in normal operation almost none is in use; they exist for stalls, not for
flow. And **the headstage MCU is the only lane without a gap in it**,
which makes the asymmetry for future work explicit: anything costing
headstage CPU comes out of the one budget already spent, while anything
costing link or host time is close to free.

## Summary

No firmware, RTL or app code was touched. Nothing is implemented.

---

## 1. The diagnosis

The system is a **free-running producer feeding a variable-capacity
transport that cannot exert backpressure**, through a finite buffer. For
that shape the governing condition is λ < μ, and everything else follows.

Before the 2026-08-27 retune, λ = 29,348 SPS and delivery matched it
comfortably. After, λ = 29,999.97 against delivery of 29,482.9 SPS
(499.7 pkt/s) with **underrun at 0%** — the read side never starved, so
`fifo0` was *accumulating*, not draining. ρ ≥ 1.

That is why the 2026-08-03 mblock-margin fix does not apply a second
time. **It was a variance fix for a variance problem**, and it worked
because λ sat well below μ at the time. This is a mean-rate problem, and
no buffer size solves a mean-rate problem — depth only changes how long
failure takes to become visible.

The separation that had been missing:

| Parameter | Sets | Formula |
|---|---|---|
| Buffer depth `B` | how long a stall is survived | `B ≥ λ × T_stall_max` |
| Margin `m = (μ−λ)/λ` | how long recovery takes | `T_recover = T_stall / m` |

Depth is fine — ~205 ms on the headstage against a ~22 ms worst measured
stall, roughly 10×. Margin is ~0.69%, so recovery from a single 22 ms
stall takes **3.1 s**, and stalls arriving more often than that
accumulate backlog no matter how deep the buffers are. The project had
been turning the depth knob at a margin problem.

**Correction found while checking the numbers:** `fifo0` is ~137 ms, not
the ~34 ms that CLAUDE.md and this morning's log both state. It was
deepened 1024→4096 frames on 2026-07-31 (`ADDR_WIDTH` 10→12);
`stream_app.c:226-229` is right and the docs are stale. It matters
because that figure feeds every buffer-sizing argument. Added to B.1's
ground-truth audit.

## 2. Two silent loss points, found by reading the source

Neither was being looked for; both came out of tracing where loss could
actually occur, to write §7 of the spec.

- **`fifo.v:58` is `else if (wen && !full)`.** On full, the write is
  silently discarded — no counter, no latched flag, `fifo_full` reaching
  only `cmd_is_00` (itself T3.3's debug hijack). This is the **single
  uncontrolled loss point in the headstage**, and its invisibility is
  exactly why yesterday's deficit had to be inferred from delivered-rate
  arithmetic instead of read off a counter.
- **`stream_app.c:1098-1103`**, the `flow_off:` path, clamps its 59-pair
  push to whatever ring room remains and discards the remainder silently.
  `StreamContinuousPollDuringStall` (`:826-835`) has the same shape. Only
  reachable when the ring is already full, but real and uncounted.

The good news from the same trace: **backpressure elsewhere is already
correct.** A full MCU ring stops `StreamIngestDuringStall`, which pushes
pressure back onto `fifo0` rather than dropping. So the loss inventory is
short and the fix is two counters, not an architecture change.

Worth naming the pattern: this morning's session found six things by
*drawing* the architecture, and this one found two by *specifying* it.
Both times the documentation act was the bug-finding act, and neither was
looking for bugs.

## 3. Decisions

**Lossless-by-margin (option A).** λ is set below measured transport
capacity — `λ_aggregate < μ_low`, with `m` ≥ the stall duty cycle — and
v1 claims zero sample loss for a stated duration at a stated rate. The
rejected alternative was "loss-accounted": run at the nominal rate and
report every loss honestly. Rejected because a complete recording is
worth more to every downstream analysis than a round number, and because
**30,000 SPS is a target, not a requirement** — A.6.5's sidecar records
the real rate either way.

**Build the loss-accounting machinery anyway.** The counters that would
have reported loss under option B are the counters that *prove* option
A's claim, and they are the only way to size `fifo0` and pick `m` on
evidence rather than by guess.

**Store-and-forward through multi-second outages is foreclosed for v1.**
It needs ~120 kB/s of headstage buffering; the WB09's 64 KB, mostly taken
by the BLE stack, cannot provide it. That is a headstage-storage feature,
not a tuning parameter — which is what makes the margin invariant an
invariant rather than a preference.

## 4. The argument worth losing

Claimed, in the first pass: because a packet must carry whole frames,
`floor(236 / 2N)` quantization waste raises the packet rate for
multi-channel modes — 508.5 pkt/s at 2ch, 517.2 at 4ch, 535.7 at 8ch —
and since per-packet MCU cost is the binding constraint, **8ch@7.5k would
be infeasible at 60 kSPS aggregate** before a line of it was written.

Manuel's objection: engineer the frame so the header is constant
regardless of mode, and packets/s stays the same or reduces.

He was right, and the reason is sharper than the objection stated: **the
whole-frame constraint was only necessary because v0 carries no absolute
stream position.** With an absolute `sample_index` in the header — which
the same proposal already introduced, two paragraphs earlier — a lost
packet no longer desynchronizes the channel interleave, so a frame can
straddle a packet boundary harmlessly. The constraint and its own
justification had been proposed in the same breath.

Consequences:

- **"8ch is infeasible" is retracted.** Under a byte-stream payload it
  costs exactly the same 508.5 pkt/s as 2ch@30k.
- `packets/s = aggregate_bytes/s ÷ 236` in **every** mode.
- The header budget is now quantified: **each header byte costs
  ~2.1 pkt/s**, against roughly 3.5 pkt/s of slack. The header cannot
  grow without spending the margin the session had just decided to buy.
- Biggest practical payoff, and not the point of the argument: **B.4
  characterisation no longer multiplies by the number of modes.** `μ_low`
  measured once applies to all of them, because every mode presents the
  transport with the same packet rate and the same packet size.

## 5. The spec

`docs/interfaces/stream-packet-format.md`, 709 lines, written before any
code per working principle 5. Header stays 8 bytes — `sample_index`
(uint32), `mode_id`, `payload_samples`, `flags`, `reserved` — with
timestamps leaving the hot path entirely for a periodic anchor.

It resolves **A.6.4's DECISION 2 as option (b)**: loss reported out of
band, the `0x8000` sentinel retired entirely rather than documented
around. Loss becomes structural (`gap = sample_index − (prev_index +
prev_payload_samples)`), and attribution — FPGA overflow vs. ring
truncation vs. bridge USB backlog vs. genuine air loss — comes from
differencing the telemetry counters across the gap. That last distinction
is the one `dropped_packets` has never been able to make.

`0xDD 0x22` widened from a bridge-drop frame into **the** out-of-band
frame, carrying every counter in the chain plus the RTC anchor. Three
frame types doing one job was the outcome worth avoiding, and this
morning's B.5 item would have been the first of them.

Implementation is phased deliberately, because λ cannot be chosen before
the telemetry that measures μ exists: counter → telemetry → measure →
format. Steps 1–3 break nothing; only step 4 is breaking, and it promotes
B.6's version handshake from nice-to-have to prerequisite.

## 6. Agreement pass — four decisions

| Question | Decision |
|---|---|
| Header CRC in `reserved` | **No** — wrong layer |
| Telemetry channel | **New `0xFFF4` characteristic** |
| `mode_id` mid-stream | **No** — streaming must be stopped |
| `sample_index` width | **`uint32`**, 19.9 h wrap accepted |

**No header CRC** because BLE's link layer already CRCs and retransmits
the headstage→bridge hop. The exposed segment is bridge→PC over UART,
and there the fix is a frame-level CRC over header *and* payload emitted
by the bridge — 248 bytes instead of 8, on the hop that actually lacks
protection. That **promoted** B.2's existing "bridge UART wire format —
add CRC" item rather than merely closing a question.

**`0xFFF4` was Manuel's call and changed the spec.** The proposal had
been to reuse `0xFFF3` with an unsolicited high-bit opcode (`0x80`).
`0xFFF3`'s contract is request/response, so unsolicited traffic there
would have been safe only by *convention* — enforced nowhere, breaking
the moment anyone writes the natural code or adds an opcode with the high
bit set. That is the same "correct by assumption, not by construction"
shape as the bridge's single-producer TX ring found this morning. A
characteristic handle is enforced by GATT instead.

The cost originally argued against it — GATT table space — was a
mis-weighing of budgets: table space is flash/RAM at init, while the
scarce budget is per-packet MCU cycles on the hot path. The *real* cost
is a fourth discovery + CCCD write in the bridge's connection sequence,
which has a history of fragility — accepted because it fails loudly (no
telemetry) rather than silently misrouting a command response.

Two knock-ons: the `0x80` convention is dropped as unnecessary, and the
telemetry frame gains a `telemetry_version` byte, since it sits off the
hot path and is where future counters should accumulate.

**`mode_id` requires streaming stopped**, matching `SET_CHANNELS`, which
also closed the channel-map question as a consequence — channels cannot
change mid-stream, so the map is constant per recording and belongs in
the sidecar, not on the wire.

Two questions remain open, neither blocking: `T_fill_max` per mode (does
not bind at 2ch/30k) and whether `μ` is genuinely payload-size-
independent (confirm during step 3's measurement).

CLAUDE.md deliberately left untouched — it documents as-built, and none
of this is built (working principle 4). Noted in the spec so it is not
"fixed" later.

## 1. The scope call: Get Settings, not connect-time

The spec's §2.1 originally called for `filter_settings` to be read once
automatically at connect, the same way `channels` already behaves. Read
through what that actually requires: the only path any RHD2164 SPI
response takes back to the host is via the FPGA's live streamed channel,
so reading a filter register means transiently pointing `REG_CH_A` at the
reserved command slot (32) and back — a real, if brief, disturbance to
whatever the operator has selected.

Doing that silently on every connect was the wrong default. Manuel's
call: a dedicated **"Get Settings" button**, operator-triggered, same
STOP → act → restore → START shape as Apply. Implemented as
`diagnostics.FilterSettingsReader`, a sibling of the A.1.1 ladder's
`RungRunner` built on the same ack-gated register-console primitives, with
one constraint carried through the whole implementation: only regbank
word 80 (slot 32) and `REG_CH_A` are ever touched during the read loop —
never sampling-table slots 0–31, never `REG_CH_B` — and the restore at
the end puts the operator's channels back via `SET_CHANNELS`, verified
the same way Apply's own readback is, rather than a raw register poke.

## 2. The sidecar

day; today was the first time any of it touched code. Two gaps the spec

  register number (decimal string), value is the raw byte, not decoded
  Hz, per the spec's own scope note.
- **§2.2**, the stop()-time fields (`duration_sec`, `rows_written`,
  `auto_stop_reason`, …) — the spec named that a rewrite happens at
  `stop()` but never named the fields.

`sample_rate.channel_hz` is written as `29999.97`, sourced from the
2026-08-27 PLL retune (`stream-packet-format.md` §1.1) — explicitly *not*
`30000`, and explicitly not final: A.7 step 3 is expected to set the real
streaming rate below it deliberately (rate margin), and the config-named-
object shape exists precisely to absorb that as a value update rather
than a schema break.

## 3. Channel provenance, persisted for the first time

`main_window.py`'s Apply flow already had everything needed to know
whether the FPGA's channels were confirmed — `_on_channels_readback`
already fires on both match and mismatch — it just never *kept* the
answer anywhere durable. `_channels_state` now does, with a three-state
provenance (`unknown` / `unverified_requested` / `verified_readback`)
downgraded the instant Apply is clicked and upgraded only on a real FPGA
reply, matching the spec's `channels`/`✓ Verified`/`✗ Mismatch`
distinction that already existed for the UI label but never for the
sidecar.

## 4. GUI, incidentally

Touching `main_window.py` for the sidecar wiring surfaced two things
worth fixing in the same pass: the recording-progress label hardcoded
"/ 10:00" while `MAX_DURATION_SEC` is actually 4000 s (~66:40) — stale
from an old cap — and the window had no `closeEvent`, so quitting
mid-recording just killed the process without the sidecar's stop-time
rewrite ever running. Both fixed; `closeEvent` now stops an active
recording and the reader cleanly before the window actually closes.
