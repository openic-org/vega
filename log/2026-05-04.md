# 2026-05-04 — Session Log

## Summary

NUCLEO-WB09KE replaces the nRF52840 as the BLE-to-UART bridge. Three firmware
bugs were fixed across the bridge and the Kuntur MCU. End-to-end result:
**30 680 SPS** (520 pkt/s × 59 pairs) over BLE 2M PHY with symmetric DLE 251.
PC-app timestamp quality also fixed and a reusable plot template added.

---

## 1. WB09KE bridge — UART initialisation failure

**Symptom:** MCU stuck in `Error_Handler()` on first boot; no UART output, all
USART1 registers read zero via SWD.

**Root cause:** `UART_PERIPHCLK` is hardcoded to 16 MHz in the STM32WB0x HAL
regardless of system clock. With `UART_OVERSAMPLING_16`, BRR = 16 MHz / 2 Mbaud
= 8, which is below `UART_BRR_MIN = 16`. `HAL_UART_Init()` returns `HAL_ERROR`
and `MX_USART1_UART_Init()` calls `Error_Handler()`.

**Fix:** `wb09ke-bridge/Core/Src/main.c` — changed `UART_OVERSAMPLING_16` →
`UART_OVERSAMPLING_8`. With OVS8, BRR = 2 × 16 MHz / 2 Mbaud = 16 ≥ 16 ✓.

**Also fixed:** `pc-app/serial_reader.py` — `BAUD_RATE` was 115 200 (fine for
the nRF52840 USB CDC which is baud-insensitive). ST-LINK VCP translates to real
UART and is baud-sensitive; updated to 2 000 000.

## 2. WB09KE bridge — GATT discovery (0x88 procedure conflict)

**Symptom:** Service discovery returned 0x88 (`ATT_ERR_PROC_IN_PROGRESS`);
`svc_start_hdl` stayed 0; CCCD never found; notifications never enabled.

**Root cause:** `aci_gatt_clt_exchange_config()` (MTU exchange) was called
fire-and-forget. `aci_gatt_clt_disc_all_primary_services()` was called
immediately after while the MTU exchange ATT procedure was still in flight.

**Fix:** `wb09ke-bridge/STM32_BLE/App/vega_bridge_app.c` —
`vega_bridge_discover_all()` now calls `gatt_cmd_resp_wait()` after MTU exchange
before starting service discovery. Full sequence:

```
aci_gatt_clt_exchange_config()  → wait proc-complete
disc_all_primary_services()     → wait → Found 0xFFF0 [0x0023-0x0028]
disc_all_char_of_service()      → wait → Found 0xFFF2 value handle 0x0027
disc_all_char_desc()            → wait → Found 0xFFF2 CCCD 0x0028
aci_gatt_clt_write(CCCD, 0x01) → notifications enabled
```

## 3. Kuntur firmware — DLE + PHY sequencing

**Symptom:** Bridge throughput capped at ~9 kSPS instead of 30 kSPS.
`HCI_LE_DATA_LENGTH_CHANGE` on the bridge showed `MaxRxOctets=27` — Kuntur was
still sending 27-byte LL PDUs, fragmenting each 244-byte notification into ~10
PDUs and saturating the CI.

**Root cause:** The Kuntur firmware had no DLE call. The nRF52840 SoftDevice
negotiated DLE automatically; the WB09KE does not. The bridge correctly calls
`hci_le_set_data_length_api(251, 2120)` from its MTU response handler, but that
only extends the **bridge TX** — Kuntur's TX stayed at 27 bytes.

**First attempt:** Added `hci_le_set_data_length(conn, 251, 2120)` directly
after the existing `hci_le_set_phy()` call in `connection_complete_event`.
Result: `hci_le_set_data_length failed: 0x07` — the PHY update LL procedure was
already in progress; the BLE LL rejects a second procedure with 0x07.

**Fix** (mirrors `stm32ble-test/server`): `kuntur-mcu/STM32_BLE/App/app_ble.c`

1. In `connection_complete_event`: removed `hci_le_set_phy()`; call
   `hci_le_set_data_length(conn, 251, 2120)` instead.
2. Added `HCI_LE_DATA_LENGTH_CHANGE_SUBEVT_CODE` handler: once
   `MaxTxOctets == 251` (Kuntur TX extended), call `hci_le_set_phy()` — DLE
   procedure is now complete and PHY can proceed safely.

**Result:**

```
Kuntur: DLE 251 requested.
Kuntur: DLE UPDATE: MaxTxOctets=251 MaxRxOctets=27   ← Kuntur TX extended
Kuntur: 2M PHY requested.
Bridge: DLE: MaxTxOctets=27  MaxRxOctets=251         ← bridge RX now 251
Bridge: DLE: MaxTxOctets=251 MaxRxOctets=251         ← symmetric ✓
Bridge: PHY update: TX=2 RX=2 status=0x00
Bridge: 520 pkt/s  30 680 SPS  ✓
```

## 5. PC-app — timestamp monotonicity clamp

**Symptom (from recording analysis):** 3 965 backwards timestamp jumps
(up to −1 652 µs), Δt std dev = 324 µs, 1 538 apparent gaps covering 57% of
wall-clock time.

**Root cause:** BLE burst delivery — multiple packets arrive in a CI with nearly
identical RTC base timestamps. The STM32 sub-second counter has ~31 µs
resolution; within a burst of 4 packets the base timestamps can be identical or
slightly non-monotonic. The pc-app reconstructed per-sample timestamps directly
from packet headers with no cross-packet correction.

**Fix:** `pc-app/serial_reader.py` — after parsing each packet, if
`packet.timestamps_us[0] <= self._last_ts_us`, rebase the packet to start at
`last_ts + 33 µs`. Genuine forward gaps (missed CIs) are untouched.

**Result:** 3 965 backwards jumps → 0, Δt std dev 324 → 9 µs, apparent gaps
1 538 → 11 (only real missed CIs remain).
