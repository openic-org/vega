# 2026-07-27 — Session Log

## Summary

Restored 30 kSPS BLE throughput after diagnosing two blocking issues introduced
by the FPGA FIFO rework (`86e8340`): a hardcoded `0x8000` sentinel in the FIFO
module that blocked the MCU spin-wait, and a channel swap caused by the FPGA
writing CH1 before CH0 into the FIFO. Throughput is back at **~526 pkt/s /
31 060 SPS**. Channel swap fix (32-bit FIFO) is planned for next session.

---

## 1. Diagnosis: why 30 kSPS was lost after the FPGA rework

### 1.1 MCU `StreamSendTask` history

The original 30 303 SPS result (commit `2cfb0b3`, `analysis_20260727.png`) used
a `while(1)` tight loop calling `BLE_STACK_Tick()` once per packet:

```c
while (1) {
    FPGA_SPI_ReadSamples(pkt.samples, STREAM_PAIRS_PER_PACKET);
    tBleStatus ret = STREAM_NotifyData(&pkt, conn_handle);
    if (ret == BLE_STATUS_INSUFFICIENT_RESOURCES) goto flow_off;
    BLE_STACK_Tick();   // flush HCI buffer → LL TX queue
    continue;
flow_off:
    ...
}
```

Several experimental changes during the session (chunked reads, RTC-timed FIFO
wait, UTIL_SEQ reschedule pattern) all degraded throughput below 320 pkt/s.
The UTIL_SEQ reschedule pattern (`9de7cd1`) was the worst: 145 pkt/s — because
BLE rescheduling overhead and event cascade serialised everything.

**Resolution:** restored `stream_app.c` to the exact bytes at `2cfb0b3` via
`git checkout 2cfb0b3 -- STM32_BLE/App/stream_app.c` (commit `0349247`).

### 1.2 The real blocker: FIFO sentinel in `components.v`

After restoring the MCU code, throughput was still not back. Root cause found in
the FPGA `components.v` FIFO module:

```verilog
else if (ren && empty) begin   // FIFO empty → output 0x8000
    DOUT <= 16'h8000;
end
```

The FPGA FIFO hardcodes `0x8000` as the empty sentinel. The MCU `fpga_spi.c`
had a spin-wait on exactly that value:

```c
do { ch0 = (int16_t)spi_bb_transfer(FPGA_STREAM_CMD); }
while (ch0 == (int16_t)0x8000);
```

The FPGA fill rate (~21–29 k SPS) is lower than the MCU drain rate (31 k SPS),
so the FIFO is empty ~30% of the time. Each empty read caused the MCU to spin at
bit-bang speed (~10 µs/transfer), looping ~14 times before valid data arrived.
This consumed the entire BLE tight loop budget.

**Resolution:** removed the spin-wait from `FPGA_SPI_ReadSamples`. The `0x8000`
sentinel now passes through to the BLE stream as an in-band underrun marker
(commit `92b8a4b` on branch `fpga-fifo-sentinel`).

## 3. Results after fix

Recording: `vega_20260727_144158.csv` / bench: `bench_20260727_144125.csv`

| Metric | Value |
|---|---|
| BLE packet rate | 521–531 pkt/s (mean 526) |
| Total BLE SPS | ~31 060 |
| Valid samples (12.96 s window) | 280 093 |
| Underruns (0x8000 sentinel) | 122 299 (30.4% of total) |
| SKP events (FIFO overflow) | 8 537 (3.05% of valid) |
| Real FPGA fill rate (estimated) | ~28 600–29 300 SPS |
| CH0 step OK | 97.0% |
| CH0 DUP | 0 |
| ch1−ch0 dominant diff | +1000 (49.7% of samples) |

**Underruns (30%):** FPGA fills at ~29 k SPS, MCU drains at 31 k SPS. The
~7% average rate deficit, combined with bursty BLE reads, drains the FIFO to
empty roughly 30% of the time. Increasing FIFO size cannot fix this — it is a
rate mismatch. Fix: tune FPGA fill rate to match the target 30 k SPS.

**SKP (3%):** FIFO overflows during FPGA write bursts. A larger FIFO would
absorb these, but the correct fix is matching fill/drain rates.

**Channel swap (50/50):** The FPGA writes CH1 into the FIFO before CH0.
The MCU reads (word0, word1) = ("ch0", "ch1"), so channels are always swapped
at the individual-pair level. The 50/50 split (correct vs. swapped) is caused
by alignment drifting after FIFO empty events — the MCU pair reads sometimes
land on a CH1-first boundary and sometimes on a CH0-first boundary.

## 5. Next session: 32-bit FIFO (channel swap fix)

**Problem:** 16-bit FIFO stores CH1 and CH0 as separate words. Any one-word
alignment drift (from underrun, overflow, or timing) swaps channels permanently
until the next drift event.

**Plan:** switch FPGA FIFO to 32-bit words, one word per sample pair:

| Layer | Change |
|---|---|
| `components.v` | `DATA_WIDTH = 32`; empty sentinel → `32'h8000_8000` |
| `kuntur_fpga.v` write side | One `fifo_wen` per pair: `fifo_din = {CH0, CH1}` |
| `kuntur_fpga.v` read side | `pair_half` toggle: first MCU read → `DOUT[31:16]` (CH0), latch `DOUT[15:0]` (CH1), assert `fifo_ren`; second read → latched CH1, no `fifo_ren` |
| `fpga_spi.c` (MCU) | No changes — still two 16-bit SPI reads per pair |
| FIFO effective depth | 512 entries → 512 pairs (was 256 pairs at 16-bit) |

**Why this fixes alignment:** one FIFO pop = one complete {CH0, CH1} pair.
Alignment drift is structurally impossible regardless of underruns or overflows.

**Timing note:** `fifo_ren` asserted on the `done` pulse of the first half-read;
CH1 latch must be stable before the next NSS assertion. MCU's 12-NOP hold
(~187 ns between transfers) gives the FPGA ≥ 9 clock cycles to update — safe
at any realistic FPGA clock.
