Continues `log/2026-10-20.md`. The pattern is the one agreed yesterday in
`docs/interfaces/lvds-tunnel.md` §12 step 4 (vega `54a4547`, branch

## K4.2.2: `block_gen` (RTL by Manuel)

`kuntur` `kuntur144/fpga/kuntur_fpga/source/impl_1/kuntur_fpga.v`
(committed with this log, `kuntur` branch `session-2026-10-21-tunnel-rx`). A new module `block_gen` (`rstb`, `clk` = `wclk`,
`dout[7:0]`) is defined at the end of `kuntur_fpga.v`. Its parts:

- a 3-bit byte index `cnt0`;
- a 16-bit block counter `cnt1`, +1 when `cnt0 == 7`;
- a registered byte mux.

`dout` drives `oddrx4_1.D0..D7`, replacing yesterday's constant
`1,1,0,0,…`.

| | |

`output reg dout` has no width, so each byte assignment kept only bit 0.
`ODDRX4.D1..D7` were tied to 0, and synthesis reported nothing above
INFO. On the wire, each byte became one 11 ns bit (that byte's bit 0)
followed by 7 zeros.

The scope photos match this (IMG_1706 and IMG_1707, taken around 04:28).
Isolated narrow spikes appear only on multiples of the 87.8 ns byte
period, with 3 to 5 per 703 ns block. One 100 ns/div capture shows
spacings of 2, 1, 1, 2, 2 byte periods. That is bytes 0, 2, 4, 5, 6, 8
of a block with `cnt[0] = cnt[8] = 1`.

`` `default_nettype none `` would not have caught this, since it is a
width bug and not an undeclared net. A self-checking testbench does
(below).

## K4.2.3: testbench

`kuntur_fpga/source/impl_1/tb/block_gen_tb.sv` (committed). It
`` `include ``s `../kuntur_fpga.v` the same way `kuntur_tb.sv` does, and
elaborates only `block_gen`.

The testbench has three parts:

- **Serialiser model.** `ODDRX4` is modelled behaviourally as an 8:1
  serialiser sending D0 first. The Lattice model is only a wrapper around
  `IOLOGIC_CORE`. `wclk` is the bit clock ÷ 8, and reset is released off
  the `wclk` grid.
- **Checker (`tun_checker`).** It does what the companion receiver must
  do:
  - hunt for `A5 5A A5 5A` in the raw bit stream;
  - confirm it 64 bits later;
  - then check every block: the preamble, `01 80`, and `cnt = prev + 1`
    mod 2¹⁶.
- **Coverage.** One nominal checker runs at each of the 8 bit phases.
  Three mutants must each be **detected**:
  - **msb**: the serialiser sends D7 first. The preamble is
    bit-palindromic, so this mutant still locks, and only `01 80` and
    `cnt` catch it.
  - **slip**: 1 bit dropped.
  - **skip**: one whole block dropped. The preamble stays aligned, so only
    `cnt+1` catches it.

Run with Icarus 12, from `tb/`:

```
iverilog -g2012 -grelative-include -s block_gen_tb -o bg.vvp block_gen_tb.sv
vvp bg.vvp                 # 65,600 blocks = 46.1 ms sim, crosses the cnt wrap; ~40 s
vvp bg.vvp +blocks=2000    # quick
```

Results:

| RTL | Result |
|---|---|
| 04:32 source (`dout[7:0]`), 65,600 blocks | **ALL PASS**: 8 phases × ~65,597 blocks with 0 errors; msb, slip and skip all detected |
| 18:19 source (1-bit `dout`), 2,000 blocks | All 8 phases FAIL; no phase ever locks |

The checker itself had a bug in its first version: CONFIRM looked for the
second preamble in the wrong half of the 64-bit window. Running against
a fixed scratch copy of the RTL exposed it, and it was fixed before the
results above.

Manuel added `kuntur_fpga/tb_rtl/qrun-blockgen.f` for Questa (committed).
I have not run it. It has no `-top block_gen_tb`, so it will probably
hit the same `ODDRX4` elaboration error that `cdr_tb` had.

## Bench: the pattern on the wire (Manuel)

The 04:33 bitstream was loaded. **The pairs are now terminated** (Manuel),
which closes yesterday's "no termination" caveat. One leg of `tun_data`
was probed: IMG_1708, about 04:39, 140 ns/div, DSOX1204G (70 MHz).

| Field on the wire (LSB-first) | Seen |
|---|---|
| `A5 5A A5 5A` = `10100101 01011010 …` | dense toggling, about 350 ns |
| `cnt lo`, `cnt hi` | irregular pulses after the preamble |
| `01` `80` = `1 0000000` `0000000 1` | one isolated pulse, then **a single low run of about 140 ns (≈ 13–14 bits)**, then high into the next preamble's leading `1` |

What the photo shows:

- **Block period.** The pattern repeats about every 5 div, about 700 ns,
  against 703 ns expected. That is as close as a photo can be read.
- **Bit order is LSB-first, now confirmed on hardware.** LSB-first gives
  one 14-zero run per block. MSB-first would give two 7-zero runs split
  by `11`, and the trace does not show that. This independently agrees
  with the Radiant model's "D0 is sent out first".
- **The block boundary is easy to see.** The preamble never holds a level
  for more than 2 bits, so the long low run marks the end of each block.
- **Levels.** One terminated leg reads 380 mV pk-pk, with an average of
  1.295 V. The 04:28 photos (also terminated) measured `tun_clk` (ch 1,
  45 MHz) at 400–420 mV pk-pk and 1.34 V average. Both
  are plausible for LVDS. Pk-pk on a single leg at the edge of the scope's
  bandwidth is not a V_OD measurement, so this is not a compliance check.
- The scope's `Freq(1) 5.68 MHz` reading is meaningless on a data
  signal.

What is not yet shown:

- The value of `cnt` cannot be read from a photo; `cnt+1` is checked only
  in simulation.
- The real test is the companion's `IDDRX4` receiver locking to this
  pattern (O2b).
- The pc-app was not run, so O3 (SPI1 still working with the tunnel
  toggling) remains untested on hardware.

## Companion receiver: CDR testbench and `frame_aligner`

Spec decisions taken today, all in `docs/interfaces/lvds-tunnel.md` (committed with this log):

- **Clock chain** (§6.4): `kuntur_clk` → PLL `CLKOS` → `ECLKSYNC` → `ECLKDIV` ÷4.
- **Eye centring** (§6.6): `CLKOS` starts at 0° and sweeps one full turn in one
  direction, 280 steps of 1.286° (78 ps). Bit errors are counted at each step
  (a bathtub curve).
- **Byte alignment** (§6.6): done in fabric, with `ALIGNWD` = 0.
- **New open item O9**: IDDRX4 runs below the 100 MHz floor of the IP Catalog.

### `cdr_tb.sv` (testbench, by me)

`kuntur` `kuntur144/fpga/intan_rec_adapter/source/impl_1/tb/cdr_tb.sv`,
committed. SHA-256 at the runs below:
`e2f54230…aca52d`.

| Part | Model |
|---|---|
| Transmitter | the real `block_gen` (`kuntur_fpga.v`), serialised D0 first; `TUN_CLK` edge-aligned |
| Link | fixed delay per pair; uniform jitter on data transitions |
| PLL | `rx_eclk` = clock + `ins` + step × T/280. The PHASESTEP pins are not modelled |
| ECLKDIV ÷4 | random start phase |
| IDDRX4 | samples on both edges; first bit received in Q0 (`+q7first` puts it in Q7); Q changes 100 ps after the SCLK rising edge; a sample is random if a data edge falls within `win` before it |
| `rx_ref` | behavioural reference aligner + checker, written from §6.6 |

At each of the 280 steps the testbench:

1. re-locks `rx_ref` (two clean blocks);
2. counts bit errors over N blocks;
3. prints the bathtub;
4. finds the longest circular error-free run;
5. checks the run's centre (±3 steps) and width against the eye that the link
   timing predicts.

`rx_ref` results:

| Run | Result |
|---|---|
| defaults (`d_data` 1000, `d_clk` 1300, `ins` 2500, jitter ±400, `win` 150 ps) | PASS. Centre 176 vs predicted 175; width 128 steps |
| `+d_data=4000 +ins=900 +jitter=1500 +seed=7` | PASS. Centre 234 vs predicted 234; width 101 |
| `+q7first` | no lock at any step, so FAIL, as intended (reversed bit order) |

Two error-free runs are seen, 140 steps (180°) apart, as expected. The offset
`s` steps down by one bit each time the sweep crosses a closed region.

**Build.** `intan_rec_adapter.v` and `kuntur_fpga.v` both `` `include `` the
common modules, so they cannot share a compilation unit. The two simulators
handle this differently:

- **Questa:** `tb_rtl/qrun.f` now compiles `intan_rec_adapter.v` into its own
  library, `-makelib lib_rx … -end`. It also needs `-top cdr_tb`, added by

  fails on `ODDRX4`.
- **Icarus 12:** `frame_aligner` is cut out of the file with `awk` on every run

### `frame_aligner` (RTL by Manuel)

Inside `intan_rec_adapter.v` (committed, 18:26 version). The companion
bitstream (04:07) is older than this RTL and was never benched, so it is
**not** committed.

**Design:**

- A 16-bit window: `din_reg_0` (negedge) and `din_reg_1` (posedge).
- The byte at offset `bitsel` is `window[s+7:s]`. Four bytes are pipelined into
  `data_sa_reg_0..3`, with `reg_0` the newest.
- These are compared with `PREAMBLE` for `SEARCH_LENGTH` cycles.

**Test.** `frame_aligner` runs beside `rx_ref` at every step. The testbench
tries `bitsel` 0–7. For each one it resets the aligner, waits for `rdy`, then
reads `valid` and `bitsel_aligned`.

**Pass rule.** At every step where `rx_ref` is error-free:

- exactly one `bitsel` gives `valid`;
- its `bitsel_aligned` equals that `bitsel`;
- that `bitsel` equals `rx_ref`'s `s`.

| Version | Result |
|---|---|
| 1st: `PREAMBLE = 32'hA55AA55A`, `data_is_aligned` pulse | **FAIL** at 256/256 error-free steps |
| 1st, with only the constant changed to `5AA55AA5` (scratch copy) | PASS, 256/256 |
| 2nd: `5AA55AA5`, sticky `valid` + `bitsel_aligned`, `SEARCH_LENGTH` = 14 | **PASS** (Icarus, Questa): 256/256 default, 201/201 hard link |
| 3rd (18:26): `cnt0` wraps at `SEARCH_LENGTH` | **PASS** (Icarus, Questa): 256/256, 201/201. `intan_rec_adapter.v` SHA-256 `20f566f0…2930e2` |

In the closed parts of the eye the aligner reports "none found", never a wrong
`bitsel`. The longest search, from reset release to `rdy`, is 15 wclk.

**Bug found: the byte order of the preamble constant.** The fix sets the
convention for every later field:

- Bit k of the assembled word is the k-th bit received. The newest byte goes
  in the top bits.
- The preamble is then `32'h5AA55AA5` (bytes A5 5A A5 5A read as a
  little-endian uint32).
- In the test block, `cnt` = `b[47:32]` and the tail is `b[63:48] = 16'h8001`.
- This matches §4.1, where every field is little-endian and needs no byte
  swap.
- The wrong constant, `A55AA55A`, is the bit-reverse of the right one. It only
  matched when `cnt[7:0] = A5`, once per 256 blocks.

**False matches in the test pattern** (exhaustive over all 65,536 `cnt`
values):

- No preamble match ever appears at a wrong bit offset, so finding it once is
  enough for `bitsel`.
- One alias appears at the correct offset but two bytes late, when
  `cnt = 0x5AA5`. The checker's two-clean-blocks lock rejects it.

**Open, in `cdr` / `cdr_fsm`** (found by reading the code; not yet simulated):

- `data_is_aligned` is undriven since the port change. `aligner_valid` is the
  signal to use.
- `aligner_rst` has no default in `always @(*)`. Synthesis makes it a latch,
  and the aligner then stays in reset.
- The scan goes on after a match, and the next reset clears `bitsel_aligned`.
  The scan must either stop at the first `valid` or latch `bitsel`.
- For real frames:
  - `SEARCH_LENGTH` must cover the longest gap between preambles (about 380
    byte slots).
  - After a lock failure, the hunt must continue from the next offset, because
    the payload can produce false matches.
  - The checker also needs the byte phase (block boundary), which
    `frame_aligner` does not output yet.
