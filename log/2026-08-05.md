## 2. A.2 — writing the interface spec before implementation

Before touching any code, wrote
`docs/interfaces/channel-selection-control-plane.md` (new `docs/` tree in the
vega repo), covering the full path: `pc-app → WB09KE bridge (UART) → Kuntur
MCU (BLE 0xFFF1) → FPGA regbank (SPI0)`.

### 2.1 FPGA register protocol — opcode scheme

Traced the existing SPI0 protocol from `kuntur_fpga.v`/`components.v`: 16-bit
word, `opcode[15:14]` + `addr[13:8]` + `data[7:0]`, where the FPGA's regbank
RAM address = `addr + 128`. Today `main_controller`'s FSM only distinguishes
`opcode==01` (register write) from "everything else" (FIFO pop) — no real
4-way decode.

Manuel proposed a clean 4-opcode scheme (`00` POP / `01` WRITE / `10` READ /
`11` NOP). Reviewing it surfaced a real landmine: `fpga_spi.c`'s
`FPGA_STREAM_CMD = 0xA5A5`, the dummy TX word sent on *every* existing
sample-pop transfer, has top bits `10` purely by accident (it was never
meant to carry opcode meaning). Once `10` means "register read," every
existing streaming transfer would be misread as a register-read request
instead of a FIFO pop — this has to be fixed in the same change that lands
the new opcode decode, not treated as optional. Documented as a
breaking-change alert in the spec.

Also traced the ChA/ChB pairing invariant: `main_controller`'s FSM toggles an
internal phase on *every* SPI0 transfer regardless of opcode, and
`FPGA_SPI_ReadSamples()` assumes matched pairs. Any odd number of register
writes issued outside a paired call would silently swap ch0/ch1 in every
subsequent sample read — likely the same class of bug as the historical
32-bit FIFO channel-swap issue. Resolved by design: `FPGA_SPI_SetChannels()`
will always issue exactly 2 transfers (both registers in one call), and must
never be interleaved with an in-progress `FPGA_SPI_ReadSamples()` call.

### 2.2 Channel encoding — friendly index formula, no lookup table

Pulled the Intan RHD2164 datasheet: each chip is two 32-channel modules (A =
channels 0–31, B = 32–63), matching `ch_sel`'s 4-way mux
(`data_a0`/`data_b0`/`data_a1`/`data_b1`) and the sampling counter's 0–31
per-module cycle. 4×32 = 128, matching "2 channels of 128 available."
Derived a single-formula mapping (no lookup table needed) to live once in
Kuntur MCU firmware, so BLE/pc-app only ever see friendly indices 0–127:

```
raw_code = ((n & 0x60) << 1) | (n & 0x1F)     // n = friendly channel, 0-127
```

Every value 0–127 maps to a real, distinct channel, which also makes BLE-side
validation trivial (range check only).

Manuel confirmed the sampling counter's extra 33rd state (`sampling_max=32`,
one more than the 32 real per-module channels) is an intentional placeholder
for an alternate RHD2164 command (chip-ID or temperature-sensor read) instead
of a channel conversion — the datasheet recommends reserving 3 such slots,
this design reduces that to 1. Confirmed `rhd2164_sampling_cmd0-3`
(regbank addr 128–131) — computed by the `ram` module but not consumed by
anything downstream today — as the likely future home for that command word.
Both the opcode-decode RTL and this wiring are tracked as new A.1 follow-up
items for Manuel; neither blocks A.2's MCU/BLE/bridge/pc-app work, which can
proceed against `REG_WRITE` alone.

### 2.3 BLE 0xFFF1 command protocol

`0xFFF1` was already declared before this session (`stream.c`, "reserved for
future commands") — clarified this wasn't chosen for this feature, just
inherited; Manuel confirmed keeping it as-is. Defined a minimal 3-byte
`SET_CHANNELS` frame (`[0x01, ch_a, ch_b]`, friendly 0–127 indices), with
range validation and a note that the missing protocol-version byte is a
known, already-tracked gap (B.2) rather than solved piecemeal here.

### 2.4 Bridge UART command relay — new work, not just plumbing-through

Realized the pc-app doesn't reach `0xFFF1` directly — only the WB09KE bridge
holds the BLE connection. The bridge already calls `aci_gatt_clt_write` once
(the 0xFFF2 CCCD enable), so the write mechanism exists, but USART1 RX
currently only forwards single bytes to a debug-trace callback — a real,
new command-frame parser and GATT-write relay is needed. Defined a new
pc-app→bridge frame (distinct magic + length + opaque payload passthrough),
keeping the command vocabulary defined in exactly one place (Kuntur MCU
firmware) so the bridge doesn't need to change when commands are added.

Chose the magic bytes `0x1B`/`0xE4` were considered but the final answer,
after discussion, is **`0xCC 0x33`** (kept as originally proposed — see §4).

## 3. Bridge RAM investigation — resolved, not a blocker

A standing memory flagged the WB09KE bridge firmware's RAM as "100% (64/64
KB), needs investigation before adding features" — exactly the kind of thing
this session's new command relay would trip over. Investigated properly
instead of assuming:

- Traced the actual linker script (`stm32ble-test/client/STM32CubeIDE/STM32WB09KEVX_FLASH.ld`,
  referenced via `wb09ke-bridge/Makefile:161`): `_Min_Heap_Size = 0x0`, and
  `.stack` is placed at a **fixed absolute address** anchored to RAM's very
  top — independent of wherever the heap's location counter happens to land.
- Summed the actual claimed sections from `build/Vega_Bridge.map`: `.data` +
  `.bss` + `.bss.blueRAM` + `.noinit` (the BLE stack's `dyn_alloc_a` buffer) +
  `.stack` ≈ 21.5 KB of 64 KB (~33%).
- Confirmed zero calls to `malloc`/`calloc`/`realloc`/`free` anywhere in the
  bridge firmware, so the zero-sized heap isn't a real problem.
- **Conclusion**: the "100%" figure was almost certainly computed as
  `(highest used address − RAM start) / RAM size`, which hits exactly 100%
  simply because `.stack` sits at RAM's literal top — even though ~43 KB
  between `.noinit` and `.stack` is genuinely unclaimed. Manuel confirmed this
  matches his own suspicion about why the number seemed odd.

Bridge feature work for A.2 is unblocked. Both `PLAN.md` (B.5) and the
now-superseded memory entry were updated to reflect this.

## 4. Closing the interface spec's open questions

- **Magic bytes**: proposed `0x1B`/`0xE4` (derived from the FPGA's own 2-bit
  opcode encoding, all four opcodes concatenated + bit-complement, mirroring
  the existing `0xAA`/`0x55` data-direction magic's complementary-pair
  structure) as an alternative to the original `0xCC 0x33`. Manuel asked for
  concrete examples of "future multi-command bridge features" before
  deciding. Walked through realistic ones (bridge/headstage version query,
  link-quality query, forced reconnect, bridge diagnostic counters) and
  concluded those are answered *by the bridge itself*, not relayed to
  `0xFFF1` — meaning the real extensibility need is a destination/type byte
  **inside** the payload, not new magic bytes. `0xCC 0x33` is therefore final.
- **pc-app UI scope**: confirmed two raw friendly-index inputs (0–127) +
  Apply is the right Phase-A scope, matching the plan's explicit "polished UI
  is Phase B."
- **RHD2164 sampling-cycle placeholder**: resolved in §2.2 above.
- **Bridge RAM**: resolved in §3 above.

The spec is now marked finalized and ready for implementation; only the
non-blocking A.1 RTL dependency remains open (tracked in `PLAN.md`, Manuel's
side).

## 5. Multi-device support — parked for a future version

Manuel raised whether showing multiple Kuntur devices in the pc-app would
need additional magic-byte pairs. Concluded no — magic bytes identify frame
*type* (data vs. command), not *device*, and mixing those concerns doesn't
scale. The more likely architecture is one WB09KE bridge per device (each on
its own USB serial port), which needs **no protocol change at all** — matches
the plan's existing isolation argument (BLE buys **per-headstage** galvanic
isolation, so one device ↔ one isolated wireless link is the natural unit).
The alternative (one bridge multiplexing several BLE links over a single
UART port) would need a device/connection-ID field added inside the existing
frames, not new magic bytes. Added as a roadmap item in `PLAN.md`'s "Out"
list (v1 scope section), architecture must not preclude either path.
