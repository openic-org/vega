## 1. The offset — found by checking, not by assuming

The user's report was concrete: "channels 0-31 are for chip0 and 32-127
for chip1" and "there is an offset between the channel selected and the
one captured — this offset is 3." Both claims got checked against source
rather than implemented as stated:

- The chip/module split is actually 4-way — 0-31 chip0-A, 32-63 chip0-B,
  64-95 chip1-A, 96-127 chip1-B — confirmed in the spec's own §1a and
  `components.v`'s 4-way mux. The user's own follow-up simplified this
  back down deliberately: the Intan datasheet numbers each chip's 64
  channels as one block, and the module split doesn't matter to the
  operator, so the UI shows chip0 = 0-63 / chip1 = 64-127.
- The offset-of-3 checked out exactly, and the direction was derivable
  without guessing: `diagnostics.py`'s `ch_code()` already encodes the
  correction as hardware-confirmed fact (`SLOT_OFFSET = 3`, confirmed on
  hardware 2026-08-11); reading `fpga_spi.c` directly showed
  `FPGA_SPI_ChannelToRaw()` never applies it. `channel_mapping.py`'s
  `physical_to_wire()` was cross-checked, before being trusted, against
  **both** — `diagnostics.ch_code()` and a verbatim copy of the real
  firmware formula pasted into the test — rather than just against its
  own internal consistency (`test_channel_mapping.py`).

New development this session, changing scope: **both chips now respond**
— chip0 was dead as of the last hardware note (`diagnostics.py`'s
`PRIMARY_SRC`/`SECONDARY_SRC`); the user reported it fixed. That's what
made the offset a full-128-channel problem instead of a 64-channel one
worth deferring.

## 2. The dead zone

`corrected = (idx + 3) % 33` lands on 32 — the FPGA's reserved
command-slot position — for physical index 29 in every module (channels
29, 61, 93, 125). `FPGA_SPI_ChannelToRaw()`'s bit-insertion formula can
never produce a raw code with that bit set for *any* friendly input by
construction (it literally inserts a zero there), so those 4 channels are
not reachable via `SET_CHANNELS` at all, corrected or not — pc-app or
firmware.

Decision (user, after I flagged the structural limit rather than paper
over it): stay in pc-app anyway. New `RawChannelSetter` (`diagnostics.py`)
writes `REG_CH_A`/`REG_CH_B` (196/197) directly, ack-gated the same way
every other register write in this codebase is. One rule threaded through
both the Apply flow and `FilterSettingsReader`'s restore step: if
*either* requested channel needs the raw path, **both** go through it —
a single `SET_CHANNELS` call sets both registers together, so mixing
would let the friendly write silently clobber the raw one back to the
wrong value. Caught this while wiring `FilterSettingsReader`'s restore:
the first draft reused `physical_to_wire()`'s friendly-space output for
the raw write directly, which is wrong for a channel that individually
*would* have been friendly-reachable — needed `physical_to_raw()`
instead, a separate function that always returns the true raw code.

A second defensive fix, found while testing rather than specified up
front: `wire_to_physical()`'s inverse arithmetic produces a nonsensical
out-of-range "channel 128+" for the one wire value (`n mod 32 == 2`) that
`physical_to_wire()` never legitimately produces. Nothing in this
codebase should ever send that value, so seeing it back would mean a
corrupted or unexpected response — now raises, caught in
`_on_channels_readback`, and reported as its own failure state rather
than silently written into `_channels_state` (and from there, a
recording's sidecar).

## 3. The naming fix — the user's, not mine

My first pass proposed renaming the Ch A/Ch B spinbox labels to Ch0/Ch1
to match the graph titles. The user's objection was sharper than the
proposal: that just aliases two schemes into one, and doesn't remove the
actual confusion between "which slot did I select" and "which physical
channel is this." Their fix — make the graph titles **dynamic**, showing
the live physical channel number instead of a static label — removes the
ambiguity instead of relabelling around it. Implemented as
`GraphWidget.set_channel_titles()`, driven by the same `_channels_state`
provenance the sidecar already uses: `"Channel —"` before anything's
applied, `"Channel N (pending)"` mid-Apply, bare `"Channel N"` once
verified — one state machine now serving both the sidecar and the UI.
