# 2026-08-11 — Session Log

## Summary

The A.1.1g chain closed end to end on the desk side. `kuntur_tb.sv` became a
**self-checking** testbench — 27 SystemVerilog immediate assertions, all passing
in QuestaSim — which confirmed the ChA/ChB pairing claim and retired three
MCU-side workarounds. The MCU helpers were then rewritten against the new SPI0
protocol, along with spec sections 1, 1a and 4.1.

Two findings outweigh the checklist:

- **A latent failure that would have been misdiagnosed.** `FPGA_SPI_ReadSamples()`
  left a `FIFO_POP` pair half-open on every call. Under the A.1.1g FSM that
  would have silently eaten `STOP_STREAMING`'s first transfer, so streaming
  would never stop — presenting as the pc-app timeout already documented as an
  accepted USART-overrun limitation. Found while rewriting, not on the bench.
- **A.1.1g subsumed A.1.4.** The sampling-cycle placeholder slot turns out to be
  already wired, and uniform 16-bit regbank access removed the reason for the
  dedicated command registers it was supposed to use. The ladder's gate moved
  from A.1.4 to **A.1.1e**.

## 1. Testbench: from waveform aid to self-checking artifact

`kuntur_tb.v` → `kuntur_tb.sv`, compiled as SystemVerilog (`qrun.f` updated).
Immediate assertions (`assert (c) $display(...); else begin ... $error(...) end`)
with a pass/fail summary and `$finish`, so a red run is visible without opening
a waveform.

Structural changes:

- **`spi_xfer(word)` task handshaking on `mcu_done`** instead of the
  `#12000/#300/#600` triple that appeared 15×. There is now no settle delay to
  re-tune when SPI timing changes. Gotcha worth remembering: it must be
  level-sensitive `wait()`, not `@(negedge)` — `mcu_done` falls a few `clk2`
  cycles after `mcu_start` rises, i.e. *inside* the start pulse, so an
  edge-triggered wait misses it and blocks forever.
- `reg_write16` / `reg_read16` / `fifo_pop_pair` wrappers.
- Command-encoding functions replacing all the `data_mosi_*` parameters, which
  also cleared both housekeeping items (dead `data_mosi_a`/`_b`, and the flat
  `8'h84` that hid its field structure).

Coverage: T1 reset defaults · T2 16-bit write · T3 read settling · T4 control
taps · T5 pairing under interleaved traffic · T6 write-tag aborts · T7 broken
POP pair. 27 checks, 0 failures, 2.25 ms sim against a 4 ms guard.

## 2. The pairing claim — confirmed, and confirmed *non-vacuously*

The result A.1.1g-tb existed to get.

T5 issues four POP pairs separated by a deliberately-odd 3-transfer write, a
`REG_READ`+`NOP`, and a lone `NOP`. ChA read `0001, 0002, 0003, 0004` with ChB
exactly +1000 every time.

The part that matters: **the counters advance.** Had the FIFO been empty the
pairs would have returned the `0x8000/0x8000` underrun sentinel, which
`check_pair` accepts — and every check would have passed proving nothing. An
advancing counter shows each pair consumed a fresh entry.

Retires three MCU-side workarounds: the even-batch rule, `FPGA_SPI_Init()`'s
priming transfer, and the NOP padding.

**Correction to a recorded assumption.** `PLAN.md` claimed the RHD model's
canned `0xe7xx`/`0x81xx` would make a swap "eyeball-obvious." They never reach
the FIFO — `ch_sel` computes `data0_synced`/`data1_synced` and discards them,
emitting `{cnt0, cnt0+1000}` (`components.v:423-425`, the A.1 ramp bug). Better
for this test, not worse: the invariant becomes numeric, `ChB - ChA == 1000`,
with a slip flipping it to −1000 (= 64536). **But it dies with A.1.1e** — see §6.

## 3. A broken POP pair fails loudly, as designed

T7's incidental result. ChA jumped `0004 → 0006`: the lone POP fired `fifo_ren`
at `op_decode1`, popped entry `0005`, delivered its ChA, then aborted when the
partner was not a POP — so entry 5's ChB was never clocked out. One entry lost,
bounded, no phase slip afterwards.

This is the closest thing yet to a direct test for the historical 32-bit FIFO
channel-swap bug, and it is what made §4 findable.

## 4. The latent failure in `FPGA_SPI_ReadSamples()`

Not on any task list; found while writing the MCU rewrite.

`FPGA_SPI_Init()` discarded one transfer, then every `ReadSamples()` call issued
`2n`. The running transfer count was therefore permanently **odd**, so pairs ran
`(T1,T2) … (T117,T118)` with `T119` dangling into whatever came next. Harmless
while nothing checked.

Under the A.1.1g FSM a POP whose partner is not a POP aborts **and consumes the
offending transfer**. `STOP_STREAMING` is a `REG_WRITE` issued right after a
`ReadSamples()` call, so its tag-1 transfer would have been swallowed; tags 2
and 3 would then each abort on their own tag check, and **streaming would never
stop.**

The reason this is worth a section: it would have surfaced as the pc-app's
"no confirmation received" timeout — indistinguishable from the USART-overrun
limitation already documented and accepted in `PLAN.md` A.2. Prime candidate for
being blamed on something already known to be flaky, and burning a bench session.

**Fix:** `ReadSamples()` is now self-contained — `2n+1` transfers with a trailing
`NOP` carrier, no priming, no dangling pair. Exactly the POP-POP-NOP shape T5
validated. Costs ~5 µs per BLE packet (1 transfer in 119 at 59 pairs).

`StreamFlushFpgaFifo()` was batched at 32 pairs/call as fallout: called one pair
at a time, `2n+1` means 3 transfers per pair instead of 2 — a 50% regression on
a blocking operation bounded at 16 384 pairs. Batching amortises the NOP to
~2.03/pair. Also fixed an off-by-one in its log line, which counted the
terminating sentinel pair as a discarded sample.

**Unverified:** this changes the 30 kSPS hot path, whose `spi_bb_transfer` NOP
margins were tuned empirically against SKP rates over several sessions. Those
margins are untouched, but the transfer count per packet is not. Needs bench
validation — `FPGA_SPI_DebugDumpPairs(32, 1000)` over the debug UART gives
DUP/SKP/OFF directly, and any `OFF` means the pairing offset is wrong.

## 5. MCU rewrite and spec revision

`fpga_spi.c`/`.h` rewritten against the new protocol:

| Function | Before | After |
|---|---|---|
| `FPGA_SPI_Init` | 1 priming transfer | 0 |
| `FPGA_SPI_SetChannels` | 2, offsets 4/5 | 6, words 196/197 |
| `FPGA_SPI_ReadChannels` | 4 (incl. padding) | 3 |
| `FPGA_SPI_SetStreamEnable` | 2 | 3, word 228 |
| `FPGA_SPI_ReadStreamEnable` | 2 | 2 |
| `FPGA_SPI_ReadSamples` | `2n` + init priming | `2n+1`, self-contained |

Spec sections 1, 1a and 4.1 revised first, per working principle 5. Three
factual errors found and fixed while in there, all of which the RTL contradicts:

1. §1 said `addr` is *"ignored on `REG_READ`"*. It carries **tag 1**, with the
   target address in the data byte. Field renamed `addr` → **`tag`** — it never
   carried an address, and the mismatched name is what let the stale description
   survive.
2. §1 said a mismatched tag aborts to `op_nop3`; the RTL has only `op_nop0`
   (§1 said `op_nop0` correctly nine lines earlier).
3. §1's register table put `rhd2164_sampling_cmd0-3` at **128–131**. They are at
   `RB_CTRL_BASE + 0..3` = **192–195**. That row was also malformed — four cells
   in a three-column table. `stream_enable` word 164 → **228** in three more
   places across the spec and `PLAN.md`.

The spec is **reopened**, with a per-hop status table. The change is confined to
SPI0 — BLE 0xFFF1/0xFFF3, the bridge, and the pc-app are untouched. Sections
1/1a/4.1 are marked as *intended*, not as-built, since the MCU side is written
but unrun.

## 6. A.1.4 revisited — subsumed by A.1.1g

Prompted by asking what A.1.4 still means after the week's changes. Reading the
RTL rather than the plan:

```
cnt0 = 32  →  rb_addr1 = RB_SAMPLING_BASE + 32 = ram[80]
           →  regbank_dout1  →  rhd_dtx  →  spi1 MOSI
```

**The placeholder slot is already wired.** `rb_addr1` spans the full 0–32 range
and `ram[80]` is initialised to `RHD_READ(6'd63)`, labelled *"RHD2164 Sampling:
cmd0"* (`components.v:600`). The slot fetches and transmits that command every
frame, today. There is no consumer to wire.

**A.1.1g deleted the reason for `rhd2164_sampling_cmd0-3`.** They existed
because the sampling table was unreachable and writes were 8-bit; now `ram[80]`
is writable at full width via `reg_write16(80, cmd)`. The four registers are
dead-end wires — and `kuntur_fpga.v:76` declares only `cmd0-2`, so `cmd3` is not
even connected. They should be deleted before someone wires to them believing
they are the intended path. Frees words 192–195, and means A.3's impedance-check
DAC needs no reserved block either.

**So the ladder's gate moved to A.1.1e.** You can inject any command; you cannot
see the answer, because `ch_sel` still emits the ramp. Reading the placeholder's
result needs no new RTL either — the RHD answers two commands later, so slot
32's value lands at slot `(32+2) mod 33 = 1`, i.e. `ch_a = {2'b00, 6'd1}`. The
`ch_a` reset default already carries the comment *"Remember there is a delay of
2 SPI cycles"*.

**Do A.1.1e together with the A.1 structural fix.** Beyond the plan's own
"avoids touching `ch_sel` twice": A.1.1e kills T5's `ChB - ChA == 1000`
invariant, which exists only because of the ramp. A selectable test-pattern mode
keeps that assertion alive instead of silently voiding it — and is the same mux
`doctor` (B.6) and the B.5 pre-session self-test need to push a known pattern
through the real path on assembled hardware.

Flagged for A.1.1d: 33 slots with a fixed 2-slot delay puts slots 31 and 32's
answers at slots 0 and 1 of the *next* frame, across the `ch_is_0_redge`
boundary that latches `data0_synced`. The placeholder sits on the awkward side.

## 7. The design cannot be simulated outside Questa

This design does not simulate under **iverilog**: it compiles clean with
`-g2012`, then time stops advancing at **t = 60 ns**, right as `rhd_start` first
pulses. A bare probe with no testbench logic at all — no MCU master, no RHD
model, MISO tied low — reproduces it. Questa runs the same source correctly, so
it is an iverilog artifact rather than an RTL fault.

Leading suspect: `rhd2164_controller` (`components.v:879`), whose hand-written
sensitivity list `always@(current_state or rhd_done or cnt0_is_max)` drives
`rhd_dtx_sel` → `max` → `cnt0_is_max`, feeding back into its own list. It should
settle, since `rhd_dtx_sel` is a pure function of `current_state`, but
`always@(*)` removes the question and is the right fix regardless.

Recorded as a **B.1 item, argued as a blocker rather than a convenience** — the
existing B.1 line "wired into the CI checks so a red run blocks a merge" is
unimplementable on a licensed GUI simulator, and a contributor who cannot
simulate cannot safely change RTL. That is the same barrier as B.6's licensed
Lattice toolchain, which the plan already calls the worst OOBE blocker. Approach
recorded cheapest-first: audit the hand-written sensitivity lists, then evaluate
Verilator (`--timing`) as the CI simulator with Questa kept for waveform debug.
Required outcome: a `make sim` any contributor can run with no licensed
software.

# 2026-08-11 (part 2) — Bench session

## Summary

**The FPGA sent real neural data for the first time.** A.1.1e landed, and the
whole A.1.1 verification ladder — (a) through (e) — passed on hardware in one
session. Every throughput and SKP number this project has ever produced was
measured against `{cnt0, cnt0+1000}`; that is no longer true.

Three findings outweigh the checklist:

- **The response-delay offset is 3, not 2.** `components.v:627` has said "delay
  of 2 SPI cycles" for as long as it has existed. The RHD pipeline *is* 2
  commands, but `data_rx_*` are held registers loaded at the SPI master's
  `csbend1` while `ch_sel` latches at the start of the *following* slot. Never
  observable before now, because `dout` was always the ramp.
- **Chip 0 does not respond — half the array is dead.** Found by the first rung
  of the ladder, on its first run.
- **The design has no timing constraints at all.** Discovered while answering a
  question about MISO setup/hold. No `create_clock` anywhere.

## 1. A.1.1e — the structural fix, and the offset that wasn't needed

Manuel connected `ch_sel.dout` to `data0_synced`/`data1_synced`, moved the ramp
generator to the `kuntur_fpga.v` top level behind a named `data_source_sel`
(regbank word 229, reset default **0 = real data**), and exported `dout_en_0`
from `ch_sel` to clock it — which preserves the old ramp timing exactly rather
than approximating it with `fifo_wen`, as the spec had suggested.

An intermediate version also extended the sampling frame to 36 slots to "make
room" for the +3 pipeline. That had a blocking fault: `cnt0` never returned to
0, so `ch_is_0_redge` fired exactly once at boot and `fifo_wen` never asserted
again — the FIFO would have stayed empty forever. Caught by reading, before it
reached the bench.

It was also unnecessary. The `+3` is a **mapping** question, not a capacity one:
in steady state the RHD pipeline is always full, so it needs no slots to live
in. With the original 33-slot counter, `ch_a = v` observes slot `(v-3) mod 33`,
which is a **bijection over all 33 slots** — nothing unreachable. Reverted; the
offset lives host-side as two named constants in `pc-app/diagnostics.py`. The
36-slot version would additionally have cost ~8.3% of the sample rate (one FIFO
entry per frame, 36 slots instead of 33) while *still* leaving `ch_a = slot+3`.

**Lesson worth keeping:** the cheapest fix was the one that changed no RTL.

## 2. The register console, and why the ladder is scripts not reflashes

A.1.1's rungs needed a driver. Rather than an MCU build flag, they run over a
generic **register console** — new 0xFFF1 opcodes `0x04 REG_WRITE16` /
`0x05 REG_READ16`, reusing the existing validate-stash-defer shape, the
stopped-stream precondition and the `s_command_busy` guard. Every write's ack
carries the value **read back** from the regbank, so a 33-word table rewrite is
verified per word for free.

This reaches what `SET_CHANNELS` deliberately cannot: sampling slot 32 is
unreachable through the friendly 0-127 mapping (`raw[5:0] <= 31` always), and it
is exactly where every rung reads its answer.

Consequence: rungs are **data** in `pc-app/diagnostics.py`. Adding rung (f) is a
table entry, not a firmware change — which over-delivers on the session's
opening constraint ("run these tests in future by only modifying flags").

## 3. Two rungs the plan did not have

The first bench run showed why. Rung (a) as specified reads slot 32 via
`ch_a = 2`, which is only correct if the offset is 3 — so a wrong offset would
have produced garbage and been diagnosed as *"MISO timing wrong, or chip not
responding"*. The very first number of the session would have been misleading.

Added:

- **Rung L** — `READ(59)` into **all 33 slots**, so any `ch_a` lands on the A/B
  marker and the result cannot be confounded by the offset. Proven
  offset-independent in the test suite by passing it at five wrong offsets.
- **Rung O** — slot 32 holds `READ(59)`, every other slot `READ(63)`; sweep raw
  `ch_a` and exactly one probe reports `0x0035`. That value *is* the offset.

Ladder order is now L → O → a–d, and the dependency is real.

## 4. Bench results

| Rung | Result |
|---|---|
| **L** link integrity | `0x0035`/`0x003A` exact on chip1; chip0 `0xFFFF` |
| **O** offset | `0x0035` at `ch_a = 2` only; all others `0x0004` → **offset 3** |
| **a** link + DDR demux | passed on chip1; aborted in restore (see §6) |
| **b** pipeline offset | `I N T A N` exact across slots 28–32, in order |
| **c** chip identity | reg 63 = 4, reg 62 = 64, reg 61 = 1 — all exact |
| **d** slot alignment | `I N T A` at the frame wrap; frame-*phase* deferred |

Rung (b) is worth noting for how it fails rather than how it passed: five
*distinct* values means a wrong offset shows as a **rotation**, not an ambiguous
mismatch. There was none.

Rung (c) vindicated the `intan.vh` fix made earlier the same day —
`RHD_2164_UNIBIAMP` was `8'd0`, the datasheet says 1, and reg 61 read `0x0001`.
The old constant would have failed against correct hardware.

**The offset was also measurable without any rung.** Friendly channel 66 reads a
constant **4**: index 2 → slot `(2-3) mod 33 = 32`, the placeholder holding
`READ(63)`, whose answer is the chip ID. Under an offset of 2 the same channel
would have shown live signal. That one reading confirmed the offset, that slot
32 is fetched and transmitted every frame (A.1.4's claim, never previously
demonstrated), and rung (c)'s chip-ID check — using only the ordinary channel
selector.

## 5. Chip 0 is not responding

Sources 0/1 (`spi1_miso0`, G3/LVDS3P) read a stable `0xFFFF` on both DDR halves
— all 64 collected frames identical, no spread. Confirmed independently through
the channel selector: friendly channels 0–63 flat at ≈ −1, 64–127 carry signal.
Both chips are populated.

**Isolated to the MISO path by construction.** Both chips share
`csb`/`sck`/`mosi` from one `spi_master_rhd2164x2`, and chip1 answers perfectly,
so commands, clock and chip-select are proven good. The RTL and the constraints
treat the two pins identically — both `IO_TYPE=LVDS DIFFRESISTOR=100`. Nothing
in the design distinguishes them, which points at the physical LVDS3 pair: an
LVDS input compares P against N, and an open or mis-biased N side parks the
comparator at a rail permanently. That is exactly the stable all-ones observed.

Chip 0's *identity* is therefore also unknown — we cannot read reg 63, so we
cannot presently confirm it is even an RHD2164.

Not a v1 blocker (64 channels remain, v1 needs 2), but it is half the array.

## 6. An operational hazard I introduced

Rung (a) aborted mid-restore (`word 63: no response after 3 retries`), leaving
the sampling table partly unrestored, and every rung showed a trickle of command
timeouts recovered by retry.

Root cause was mine: every 0xFFF1 command emitted ~3 blocking `APP_DBG_MSG`
lines. At 115200 that is ~15 ms of blocking UART per command — and **USART1 is
on APB1, which the BLE radio gates**, the same hazard that forced the FPGA SPI
onto bit-banged APB0 GPIO in the first place. One line per operator click is
fine; a rung issues ~90 commands back to back.

Raising `COMMAND_GAP_MS` did not help, which was the clue: it is not a pacing
problem. Fixed by gating the high-rate prints behind
`STREAM_REG_CONSOLE_VERBOSE` (default 0); readback mismatches and malformed
frames still print unconditionally. **Needs a reflash to take effect.**

## 7. Corrections made to my own work

Recorded because each was wrong in the docs before it was right:

- **"No ARM toolchain available"** — repeated across several turns and written
  into `PLAN.md`. Wrong: the toolchain ships inside STM32CubeIDE and simply is
  not on `PATH`. Both firmwares build clean from the CLI. Now in `CLAUDE.md`.
- **Spec §1.3 demanded `CONVERT(k)` at slot `k`** on the reading that thirty
  consecutive `CONVERT(63)` meant thirty conversions of channel 63. Wrong:
  `C=63` **auto-increments**, so slot `k` already converts channel `k`, and the
  anchor re-asserts every frame. Requirement withdrawn and the reasoning written
  prominently into the spec, because thirty identical commands read like a
  copy-paste bug and will invite a "fix" that breaks it — the same trap as
  `stream_enable`'s reset default.
- **"The `ch_a`/`ch_b` defaults corroborate an offset of 3"** — they do not.
  Both readings are self-consistent; the defaults are not evidence either way.
- **`0xFFFF` read as "a WRITE response with `D=0xFF`"** — an over-reading. The
  simpler explanation, all-ones on a held line, should have led.

## 8. Host verification built this session

- **`mcu-tests/`** — compiles the **real** `Core/Src/fpga_spi.c` against stub
  HAL headers and a **pin-level model of the A.1.1g FPGA FSM**, so the bit-bang
  layer runs too. 52 checks. The load-bearing one: every public function leaves
  the FSM at its decode state — precisely the latent failure from part 1 of this
  log. **Mutation-tested**: dropping the tag-2 transfer → 23 failures; dropping
  `RegRead16`'s NOP carrier → 1; removing the slot range check → 4. The middle
  one only trips the wire-sequence assertion, since `READ`+`READ` still returns
  correct values — which is why the suite asserts sequences, not just returns.
  *One implementation note:* a level-based SCK edge detector saw zero transfers,
  because `SCK_LOW()` is overwritten by the next bit's `SCK_HIGH()` before any
  `__NOP()` runs. The fix is faithful rather than a workaround — BSRR is
  write-only "apply this edge and forget", so the model consumes each write.
- **`pc-app/test_diagnostics.py`** — runs the rung runner against a fake reader,
  proves rung L is offset-independent, proves rung O localises the offset, and
  pins the wire format including the little-endian split (a big-endian slip is
  silent: `0x95A5` arriving as `0xA595` still writes *something*).

## 9. FPGA timing constraints — raised, not started

Asked at the end of the session: how to constrain setup/hold on the LVDS MISO
inputs. Answering it surfaced that **`impl_1.pdc` has no `create_clock` at
all**, and its one SDC line references a clock that was never created. The
design is entirely unconstrained.

Full scope, the expected violation, and the four structural options are written
up in `PLAN.md` under B.1. Deliberately **not** started: real constraints change
placement and routing, which would invalidate the bitstream the ladder was just
