Recorded `vega_20260427_154845.csv` (10 s, Lenovo TB305FU, Android 15).

**Findings:**
- 83 721 samples, **7 771 SPS**, zero data loss (sawtooth intact across all 1 419 packets)
- All packets exactly 59 samples ✓
- Timestamps monotonically increasing ✓
- Root cause of "issues": Lenovo BLE scheduler uses a **variable CI (15–45 ms)**, delivering data in bursts of 1–18 packets per connection event instead of a steady 2 pkt/CI
- Long gaps (>15 ms): 6.3 % — caused by delayed CI, NOT dropped packets (STM32 ring buffer absorbs)
- The `CONNECTION_PRIORITY_HIGH` Android hint was already achieving ~14 ms effective CI

## 3. CPUP fix — STM32 → Android CI negotiation

**Problem:** The CPUP (`aci_l2cap_connection_parameter_update_req`) was sent immediately alongside `hci_le_set_phy`, causing both negotiations to race on a freshly-formed link.

**Fix in `app_ble.c`:**
- Moved CPUP to fire **after** `HCI_LE_PHY_UPDATE_COMPLETE` (link fully settled)
- Widened target range from 7.5–11.25 ms → **7.5–15 ms** (more likely to be accepted)
- Added **retry** in `HCI_LE_CONNECTION_UPDATE_COMPLETE`: if granted CI > 15 ms, re-request once
- Added PHY result logging (`TX=2M RX=2M status=0x00` confirmed on Lenovo)

**UART log result:**
```
PHY update: TX=2M RX=2M status=0x00
CPUP: sent after PHY settle — CI 7.5–15 ms requested.
CPUP: Android ACCEPTED the CI update (7.5–15 ms).
Connection Interval: 15.00 ms  ← confirmed
```

Second CSV (`vega_20260427_170849.csv`) showed identical pattern to the first — the Lenovo's effective CI was already ~14 ms via `CONNECTION_PRIORITY_HIGH`, so CPUP confirmed rather than changed the CI. CPUP remains a safety net for hosts that don't set HIGH priority.

## 5. STREAM_MODE_LENOVO_SMOOTH (mode 2)

**Goal:** Replace the bursty 1–18 pkt/CI delivery pattern with perfectly regular 1 pkt/CI.

**Key insight:** Removing `BLEStack_Process_Schedule()` + the `UTIL_SEQ_SetTask` self-reschedule after each send means the BLE stack only commits **one notification per connection event**, regardless of VTIMER rate. The VTIMER becomes a safety fallback only.

**Changes:**

| File | Change |
|---|---|
| `stream_app.h` | Added `STREAM_MODE_LENOVO_SMOOTH = 2`; set as active |
| `stream_app.c` | `STREAM_SEND_PERIOD_MS = 36U` (~13.9 ms actual); burst pipeline wrapped in `#if != LENOVO_SMOOTH` |
| `app_ble.c` | Added `"Kuntur-S"` device name and advertising data for mode 2 |
| `BleManager.kt` | `DELIVERED_SPS = 4_000L`; old 7 725 kept as commented line |

**CSV result (`vega_20260427_172511.csv`, 10 s):**

| Metric | ANDROID_BLE burst | **LENOVO_SMOOTH** |
|---|---|---|
| SPS | 7 771 | **1 641** |
| Sawtooth breaks | 0 | **0** |
| Burst packets/CI | 1–18 | **1 (100%)** |
| Inter-packet gap range | 3–39.8 ms | **33.8–34.4 ms** |
| SPS variance (per second) | 6 313–8 083 | **1 593–1 652** |

SPS is 1 641 (not 4 000) because the Lenovo negotiated a ~34 ms CI in this session. At 1 pkt/CI: 1 000/34 × 59 = 1 735 SPS theoretical ≈ 1 641 measured. The ±0.3 ms jitter is the tightest inter-packet consistency observed across all sessions. Graph scrolls at a perfectly constant rate.

All mode parameters saved to memory (`project_stream_modes.md`).
