## 2. What the hardware actually provides — checked, not recalled

Every physical-layer number in the spec is read out of
`kuntur144-ecl.kicad_pcb`, `kuntur144-omnetics.kicad_pcb`, and the
2026-08-31 Radiant build's `.pad` / `.mrp` reports. Four findings that
were not previously written down anywhere:

- **Only two differential pairs reach the uHDMI.** `FPGA_LVDS1`
  (J1 pads 3/5 → FPGA G9/F9) and `FPGA_LVDS2` (pads 6/8 → E9/E8). HDMI's
  third pair (`D0±`, pads 9/11) is physically present on the connector
  and **unrouted on the board**. So there is no spare pair to forward a
  clock on: one pair per direction, each self-timed, receiver recovers
  timing from the data. Nearly every framing and coding decision in the
  spec descends from this single fact.
- **Both pairs are bottom-bank (bank 5) and true `LVDS_OUT` works there.**
  Not inferred from the CrossLink-NX datasheet's bottom-I/O rule —
  demonstrated: `spi2_csb` (G5, `PB30A`) and `spi2_sck` (F7, `PB26A`)
  already come out of PAR as `LVDS_OUT` with `DIFFDRIVE:3.5` on this
  exact device, package and speed grade. Stronger evidence than the
  datasheet, and it was sitting in a build report the whole time.
- **The TX/RX pair assignment is backwards and must swap.** G9/F9 is
  `PCLKT5_0`/`PCLKC5_0`, a primary-clock *input* pair; E9/E8 is not.
  Today's `TEST ONLY` passthrough in `kuntur_fpga.v` puts `serial_lvds_tx`
  on the clock-capable pair. Costs nothing to fix — the pigtail is
  hand-made, so this is a port-direction flip plus four `.pdc` lines, **no
  PCB change** — but it has to happen before the pigtail is soldered.
  (Also worth renaming both ports: `serial_lvds_rx` is currently declared
  `output`, with the `input` version commented out one line above it.)
- **Resource headroom:** 1 of 2 PLLs free, 0 of 102 IDDR/ODDR primitives
  used, 4% logic — but **PIOs at 31/39**, going to 33/39 once both pairs
  become differential. Logic is not the constraint here; pins are.

## 3. The constraint that decided the architecture before any decision did

The Intan controller is the SPI **master** — confirmed from
`kuntur144-omnetics.kicad_pcb`'s J1, the 12-pin Omnetics carrying
`CSb±/SCLK±/MOSI±/MISO0±/MISO1±`, i.e. exactly an RHD2164 slave
interface. An RHD2164 must answer MISO within the same transaction
(`tMISO` = 12 ns, the same datasheet figure `fpga-timing-constraints.md`
§3 already uses).

The most optimistic possible tunnel round trip — one minimal frame each
way plus one RHD2164 SPI slot, with zero attributed to pipelining, comma
alignment or CRC — is ≳ 2.1 µs. That floor is already ~175× the budget.

So a **transparent SPI bridge is arithmetically impossible**, and the
companion FPGA must be an RHD2164 *emulator* answering from a replicated
buffer. This was settled before asking Manuel anything, because it is not
a preference.

## 4. Three decisions (Manuel), and A.5 falling out of one of them

1. **Kuntur owns AFE configuration exclusively.** The Intan controller is
   *a visualiser of the data the FPGA gets*; Kuntur's real register state
   is replicated downstream so the controller's reads return live truth,
   not an echo of its own writes.
2. **Free-running clocks with sync markers**, not loop timing — Kuntur
   keeps its own PLL off `clkin` whether or not the cable is attached, so
   the BLE stream's sample rate does not change between wireless and
   wired mode and A.6.5's recorded `sample_rate` / A.7's λ stay valid.
3. **All 128 channels cross downstream.**

Decision 1 **discharges A.5 by construction.** A.5 exists because "two
masters want the AFE" and "if the Intan controller reconfigures
gain/bandwidth mid-session, the BLE recording silently changes meaning."
With no path at all from the Intan controller to the RHD2164 registers,
there is no arbiter to build and no ambiguous ownership mode to get
wrong. Host writes are absorbed with a datasheet-correct ack (so the
Intan protocol never stalls), not applied, and reported upstream.

The cost is a **runbook change**, tracked as spec item O6: the operator
configures via Vega, not via the Intan software, and a `READ` after a
host `WRITE` returns Kuntur's value rather than the written one. Intended
— but it will read as a hardware fault to anyone who does not know, so it
belongs in the bench procedure before the animal test, not after.

## 5. Numbers the spec pins, and one that cross-checks

- 33 slots × 46 `clk` = **1518 clk** per sampling frame; 45,539,955 /
  1518 = **29,999.97 Hz**. That is an independent re-derivation of
  A.6.5's recorded `sample_rate.channel_hz`, arrived at from the FSM
  state count and the PLL constraint rather than from the retune note.
  Two separate derivations agreeing is worth more than either alone.
- 32 conversion slots × 4 MISO halves × 16 bit = 256 B/frame →
  **61.44 Mbit/s**; 64.32 with framing + CRC-32; 80.4 minimum line rate
  after 8b/10b.
- Recommended symbol clock **`clk`/2 = 227.7 Mbps** (759 symbol slots per
  sampling frame exactly, 35% utilised), `clk`/3 as fallback. `clk`/4 is
  disqualified structurally rather than by judgement: 1518 = 2·3·11·23,
  so it cannot yield a whole number of symbol slots per frame.
- Latency budget ≈ **58–92 µs** ADC → Omnetics connector, two thirds of
  which is waiting for the sampling frame to complete and cannot be
  improved by any link change.

## 6. Two safety-shaped requirements worth calling out

- **On link loss or CRC failure the companion serves `0x8000`, never
  repeated data.** Reuses the project's existing underrun sentinel
  (`fifo.v` returns `{2{16'h8000}}`, and the pc-app already counts it —
  that is how 2026-08-31's 0.4% genuine underrun was measured). Under
  `RHD_TWOSCMP = 1` it rails full-scale negative on every channel at
  once, which is visually unmistakable. A repeated-frame fallback would
  instead look like a *quiet, stable recording* — the worst possible
  appearance for a dead cable during a procedure.
- **`flags` bit 1 announces the test pattern in band.** A.1's original
  defect was that every metric in the entire SKP investigation measured a
  synthetic ramp with nothing on the wire saying so. A readout being
  compared against a reference instrument has to state whether it is
  showing real silicon.

## 7. A duplication hazard flagged before it happens

The `SLOT_OFFSET = 3` pipeline correction (RHD2164 returns a `CONVERT`
result two commands later) currently lives in the pc-app —
`channel_mapping.py`, added 2026-08-29 under an explicit instruction not
to touch firmware — and in `diagnostics.py`, while `FPGA_SPI_ChannelToRaw()`
does not apply it at all. If the companion FPGA implements it too, one
hardware fact will exist in three implementations.

That divergence is exactly what produced the offset bug in the first
place. The spec therefore carries the tunnel raw and slot-indexed, with
interpretation as the receiver's job, and O4 asks that the offset be
fixed at source before the companion becomes the third copy.

## 8. O2 resolved the same session — and it resolved better than expected

Took O2 immediately after the spec landed. The question was whether
LIFCL has hardened 10:1 gearing for 8b/10b or whether an 8→10 fabric
gearbox would be needed. Answered against the **installed Radiant
2025.2.1 LIFCL primitive library**, not from recollection:

- **`ODDRX5` / `IDDRX5` are hardened 10:1** — `D0..D9`, `SCLK` =
  `ECLK`/5, DDR on `ECLK`. One 8b/10b symbol = one word = one `SCLK`
  cycle. No gearbox, no rate conversion. Full ladder available:
  `ODDRX1` 2:1, `ODDRX2` 4:1, `ODDR71` 7:1, `ODDRX4` 8:1, `ODDRX5` 10:1.
- **`IDDRX5` has `ALIGNWD`** — *"shift the word by one bit"* — so comma
  alignment is a hardware barrel shift, not a fabric barrel shifter plus
  a 10-way parallel comma comparator at each end.

The better find was the clocking. The 227.7 Mbps recommendation, chosen
in §6.2 purely on framing arithmetic, turns out to land on **exact
integer dividers off `pll0`'s existing VCO** — the one configured for the
2026-08-27 30,000 SPS retune, for entirely unrelated reasons.
`FVCO = 1593.898438 MHz`:

| Clock | Divider | Frequency |
|---|---|---|
| `clk` | /35 | 45.5399554 MHz *(existing)* |
| `ECLK` | **/21** | 75.8999256 MHz → **151.799851 Mbps** |
| `SCLK` | **/105** | 15.1799851 MHz = one symbol per cycle |

A clean 3:5:1 ratio. *(These are the corrected 2026-09-03 dividers — see
§9. The session first recommended `clk`/2, i.e. /14 and /70 for
227.7 Mbps.)* Legality checked against the PLL IP's own
`PARAM_RANGE` table (`ip/lifcl/pll/plugin/plugin.py`) rather than assumed:
`O_DIV` 1–128, `FVCO` 800–1600 MHz, `FOUT_F` 6.25–800 MHz — all three
dividers valid (as are /14 and /70). `pll0` already exposes six outputs with four disabled, so
`CLKOS2`/`CLKOS3` take `ECLK`/`SCLK`.

Consequences: **no second PLL** (the free one stays free, correcting §1.4
of the spec as first written), and **no clock-domain crossing** between
the sampling domain and the tunnel domain — the transmitter can read
`spi_master_rhd2164x2`'s capture registers with no synchroniser, no async
FIFO and no CDC exception in the `.sdc`. The "759 symbol slots per
sampling frame" figure becomes a property of the clock tree rather than an
arithmetic coincidence.

One number remains unverified locally and is stated as such in the spec:
the max `ECLK` frequency / LVDS data rate for `LIFCL-17-8` bank 5 is an AC
table not present in the installed toolchain. 113.85 MHz / 227.7 Mbps is
far below any published CrossLink-NX figure for a display-bridge part, but
it is flagged rather than assumed, and O7's bench bring-up settles it.
